# AI 평가 (Evaluation)

기획서 §11의 Q1~Q6를 실제 법령·실제 모델로 측정한다.

```bash
.venv/bin/python scripts/run_eval.py --save              # 실행 + 결과 저장
.venv/bin/python scripts/run_eval.py --offline           # 캐시된 snapshot만 사용 (재현)
.venv/bin/python scripts/run_eval.py --model gpt-4o-mini # 모델 비교
.venv/bin/python scripts/run_eval.py --dataset evaluation/datasets/holdout_v1.json --rag  # 홀드아웃
```

첫 실행은 법제처에서 법령을 받아 `evaluation/.snapshots/`에 캐시한다. 이후
`--offline`로 돌리면 **같은 입력**에 대해 모델만 바꿔 비교할 수 있다 (AP-07).

## 홀드아웃 실측 (2026-09-21, holdout_v1 · 16케이스, gpt-4o)

> **이 절의 수치는 두 시점이 있다.** 1차는 법률↔시행령 페어링(ADR-025) 이전,
> 2차는 이후다. 1차가 결함을 드러냈고 2차가 고친 뒤의 값이다.

| 지표 | 개발셋 | 홀드아웃 1차 | **홀드아웃 2차** |
|---|---|---|---|
| 판정 정확도 | 100% | 62.5% | **100%** |
| 과도한 보류율 | 0% | 42.9% | **0%** |
| 위임 케이스의 보류율 | 50% | 100% | **10%** |
| Q1 노출 인용 정확도 | 100% | 100% | 100% |
| └ 모델 생성 인용 정확도 | 100% | 83.8% | 96.4% |
| Q2~Q6 | 전부 달성 | 전부 달성 | 전부 달성 |
| latency p50 / p95 | 6.6s / 10.0s | 10.8s / 17.0s | 7.8s / 12.8s |

### 2차 100%를 깨끗한 홀드아웃 수치로 읽으면 안 된다

프롬프트·룰을 홀드아웃 결과에 맞춰 조정하지는 않았다. 고친 곳은 전부 개발셋에서
검증했고, 개발셋은 100%를 유지했다(회귀 없음). 그러나 **무엇을 고쳐야 하는지는
홀드아웃의 실패 양상을 보고 알았다.** 그 정보가 설계에 들어간 이상 이 16건은
더 이상 "본 적 없는 데이터"가 아니다.

`holdout_v1`은 세 번 실행됐다 — 진단 1회, 수정 확인 1회, 정규식 버그 수정 후
재확인 1회. 운용 규칙대로 **이 셋은 튜닝 목적으로는 소진됐다.** 다음 일반화
주장에는 `holdout_v2`가 필요하다.

정직하게 말하면 이 100%가 뒷받침하는 것은 "62.5%를 만든 결함이 실제로 고쳐졌고
개발셋을 망가뜨리지 않았다"까지다. "이 시스템의 일반화 정확도가 100%"가 아니다.

### 1차(62.5%)가 드러낸 것 — 오답 6건이 전부 같은 결함


데이터셋은 개발셋과 법령이 겹치지 않고(최저임금법·채용절차법·근로자퇴직급여 보장법·
건설산업기본법·의료법·파견근로자보호법), 프로필 2종(인력공급, 의료)을 새로 넣었다.
라벨은 실행 전에 확정했고, 1차 실행 결과를 보고 고치지 않았다.

오답 6건이 모두 `→ HOLD`였고, 위임 유무로 정확히 갈렸다.

| | 케이스 | 정확도 |
|---|---|---|
| 조문에 위임 문구 **없음** | 6건 | **100%** (6/6) |
| 조문에 위임 문구 **있음** | 10건 | **40%** (4/10) |

위임이 있으면서 정답이 APPLICABLE인 5건(H04, H06~H09)은 **5건 모두** HOLD로 갔다.
즉 **위임 문구가 감지되고 사용자가 대상 집단에 속하면 APPLICABLE이 절대 나오지 않는다.**
ADR-011("적용을 가르는 핵심 기준이 위임되면 보류")을 조건부 원칙이 아니라 무조건 규칙으로
적용하고 있다. 최저임금법 제6조의 위임은 *산입 임금의 범위*에 관한 것이지 최저임금
지급 의무 자체를 좌우하지 않는데도 보류가 나왔다 — 사용자에게는 "최저임금을 줘야 하는지
모르겠다"는 답이 되므로 제품으로서 실패다.

개발셋에는 이 패턴(위임 있음 + 정답 APPLICABLE)이 사실상 없었다. 3회차 프롬프트 수정이
개발셋의 반대 방향 오답(위임 있음 + 정답 NOT_APPLICABLE)만 보고 이뤄졌기 때문에,
경계가 한쪽으로 치우친 채로 100%가 나온 것이다.

### 어떻게 고쳤나 — 법률↔시행령 페어링 (ADR-025~027)

진짜 원인은 프롬프트가 아니라 **코드**였다. `deterministic_hold_reasons`가 위임
문구만 있으면 LLM 판정과 무관하게 HOLD로 강등하고 있었다. 프롬프트는 이미 "부수적
위임은 보류 사유가 아니다"라고 쓰고 있었지만 코드가 그 위에서 덮어썼다.

위임된 하위법령 조문을 찾아 근거로 함께 준다. 시행령 조문이 "법 제6조제4항에 따라"로
모법을 직접 참조하므로 역매핑이 가능하다 — 추론이 아니라 원문에 적힌 사실이다.
강등 조건도 '위임이 있는가'에서 **'기준을 손에 넣었는가'**로 바꿨다.

만들면서 세 번 조였다. 세 번 다 실제 법령에서 틀린 뒤에 알았다.

| 문제 | 증상 | 조치 |
|---|---|---|
| 타법 참조를 모법으로 오인 | 시행령의 "근로기준법 제50조"를 모법 제50조로 색인 | 앞 글자가 한글이면 제외 (맨 '법'만 모법) |
| 스쳐가는 참조를 이행 조문으로 오인 | 개인정보 보호법 제31조에 무관한 시행령 조문 3건이 근거로 붙음 | 각 항의 **근거 절**에서만 인정 (ADR-026) |
| 재위임을 해소로 오인 | 산안법 시행령 제16조 "별표 3과 같다"를 붙였더니 150인 제조업이 **무관**으로 판정 | 맨 앞 이행 조문이 기준을 담을 때만 보류 해제 (ADR-027) |

마지막 것이 가장 위험했다. 보류가 무관으로 바뀌는 것은 개선이 아니라 **더 나쁜 실패**다.
관련 규제를 놓치는 쪽이 보류보다 나쁘다는 원칙(NFR-003)이 없었으면 "보류율이 줄었다"고
자축했을 수치다.

덤으로 같은 버그를 두 번 밟은 것도 확인했다. `정하`가 `정한다`에 매치되지 않는
한국어 활용 문제를 diff 엔진에서 이미 고쳤는데 페어링 모듈에서 똑같이 재현했다.
활용형 패턴을 `DELEGATION_VERB` 공개 상수로 올려 두 곳이 같이 쓰게 했다.

### RAG는 이 16건에서 0건 검색됐다

`--rag`로 돌렸지만 참고자료가 붙은 케이스는 0%다. 버그가 아니라 **인덱스 커버리지**다.
현재 Chroma 인덱스에는 개발셋 5개 법령의 해석례·판례만 적재돼 있고 홀드아웃 6개 법령은
하나도 없다. 뒤집어 말하면 **개발셋의 100%는 그 5개 법령용으로 맞춰 적재한 인덱스 위에서
나온 수치**이며, 임의의 법령을 조회하는 실사용 상황은 RAG 없이 돌아가는 홀드아웃 쪽에
가깝다. 인덱스를 넓히기 전까지 RAG 기여분을 성능으로 주장하지 않는다.

## 이 수치를 읽을 때의 주의

1. **양쪽 다 이제 개발셋이다.** `applicability_v1`은 처음부터 그랬고, `holdout_v1`도
   ADR-025 설계에 그 실패 양상이 반영된 이상 더 이상 미지의 데이터가 아니다.
   일반화 성능을 주장하려면 `holdout_v2`가 필요하다.
2. **표본이 작다.** 개발셋 15건, 홀드아웃 16건. 케이스 1건이 6~7%p를 움직이므로
   신뢰구간을 논할 크기가 아니다. 홀드아웃의 HOLD 케이스는 2건뿐이라 보류 판정의
   정밀도는 사실상 측정되지 않았다.
3. **Q3는 대리 지표다.** 기획서의 Q3는 사용자가 실제로 행동했는지를 보는 제품 지표이고,
   여기서는 '해당 판정이 ACTION/DECISION으로 분류된 비율'로 근사했다.
4. **Q1은 두 값이다.** 사용자에게 노출되는 인용은 Validator 통과분이라 구조적으로
   100%다. 모델이 만든 인용 자체의 정확도가 그 아래 값이고, 둘의 차이가
   Validator가 막아낸 양이다.

## 정답 라벨 기준

`gold_applicability`는 **이 시스템이 주어진 입력으로 내려야 하는 판정**이다.
따라서 구체 기준이 하위법령에 위임된 조문은 HOLD가 정답이다 (BR-003).
라벨은 조문 원문을 직접 읽고 부여했으며, 근거를 각 케이스의 `note`에 적었다.

## 알려진 한계

근로기준법 제76조의2(직장 내 괴롭힘 금지)는 조문 문언에 규모 조건이 없지만 실제로는
5인 미만 사업장에 적용되지 않는다(시행령 별표1). 4인 프로필 케이스를 평가셋에서 제외했다.

**법률↔시행령 페어링(ADR-025)이 붙은 뒤에도 이 케이스는 아직 못 넣는다.** 기준이
시행령 *조문*이 아니라 *별표*에 있고, 별표는 법제처 조문 본문에 딸려 오지 않기
때문이다. 현재는 별표로 넘기는 조문을 '기준 미확보'로 보아 보류를 유지한다
(ADR-027). 별표 조회를 붙이면 이 케이스를 추가한다.

## 홀드아웃 운용 규칙

1. `holdout_v1`의 결과를 보고 프롬프트·룰을 고치지 않는다. 고치면 홀드아웃이 아니다.
2. 결함을 고칠 때는 개발셋(또는 새 개발셋)에서 고치고, **그 뒤에 홀드아웃을 다시 돌려**
   개선이 일반화됐는지 본다.
3. 홀드아웃을 여러 번 돌려 그 수치를 보고 의사결정을 반복하면 그 셋도 오염된다.
   **`holdout_v1`은 소진됐다** — 진단 1회, 수정 확인 1회, 정규식 버그 수정 후 재확인
   1회로 세 번 실행했다. 회귀 확인용으로는 계속 쓰되, 일반화 주장의 근거로는 쓰지
   않는다. 다음 일반화 주장 전에 `holdout_v2`를 만든다.
4. 라벨은 실행 전에 확정한다. 결과를 보고 라벨을 바꾸지 않는다.
