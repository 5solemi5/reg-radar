# AI 평가 (Evaluation)

기획서 §11의 Q1~Q6를 실제 법령·실제 모델로 측정한다.

```bash
.venv/bin/python scripts/run_eval.py --save              # 실행 + 결과 저장
.venv/bin/python scripts/run_eval.py --offline           # 캐시된 snapshot만 사용 (재현)
.venv/bin/python scripts/run_eval.py --model gpt-4o-mini # 모델 비교
.venv/bin/python scripts/run_eval.py --dataset evaluation/datasets/holdout_v1.json --rag  # 홀드아웃
```

첫 실행은 법제처에서 법령을 받아 `evaluation/.snapshots/`에 캐시한다. 이후
`--offline`로 돌리면 **같은 입력**에 대해 모델만 바꿔 비교할 수 있다 (AP-07).

## 홀드아웃 실측 (2026-09-21, holdout_v1 · 16케이스, gpt-4o)

개발셋 100%가 과적합인지 확인하기 위해, 프롬프트 수정에 **한 번도 쓰지 않은**
데이터셋을 만들어 **한 번만** 돌리고 그 수치를 그대로 기록했다. 법령은 개발셋과
겹치지 않고(최저임금법·채용절차법·근로자퇴직급여 보장법·건설산업기본법·의료법·
파견근로자보호법), 프로필 2종(인력공급, 의료)을 새로 넣었다.

**개발셋 100%는 일반화되지 않는다.** 실제 성능은 62.5%로 봐야 한다.

### 오답 6건은 전부 같은 결함이다

오답 6건이 모두 `→ HOLD`이고, 위임 유무로 정확히 갈린다.

| | 케이스 | 정확도 |
|---|---|---|
| 조문에 위임 문구 **없음** | 6건 | **100%** (6/6) |
| 조문에 위임 문구 **있음** | 10건 | **40%** (4/10) |

위임이 있으면서 정답이 APPLICABLE인 5건(H04, H06~H09)은 **5건 모두** HOLD로 갔다.
즉 **위임 문구가 감지되고 사용자가 대상 집단에 속하면 APPLICABLE이 절대 나오지 않는다.**
ADR-011("적용을 가르는 핵심 기준이 위임되면 보류")을 조건부 원칙이 아니라 무조건 규칙으로
적용하고 있다. 최저임금법 제6조의 위임은 *산입 임금의 범위*에 관한 것이지 최저임금
지급 의무 자체를 좌우하지 않는데도 보류가 나왔다 — 사용자에게는 "최저임금을 줘야 하는지
모르겠다"는 답이 되므로 제품으로서 실패다.

개발셋에는 이 패턴(위임 있음 + 정답 APPLICABLE)이 사실상 없었다. 3회차 프롬프트 수정이
개발셋의 반대 방향 오답(위임 있음 + 정답 NOT_APPLICABLE)만 보고 이뤄졌기 때문에,
경계가 한쪽으로 치우친 채로 100%가 나온 것이다.

**이 결함은 이 데이터셋으로 고치지 않는다.** 고치는 순간 홀드아웃이 아니게 된다.
근본 해법은 로드맵에 이미 있는 **법률↔시행령 페어링**이다 — 위임된 하위법령 조문을
같이 붙여주면 "위임됐으니 모른다"가 아니라 실제 기준을 보고 판정할 수 있다.
이 홀드아웃이 그 작업의 우선순위를 뒷받침하는 실측 근거다.

### RAG는 이 16건에서 0건 검색됐다

`--rag`로 돌렸지만 참고자료가 붙은 케이스는 0%다. 버그가 아니라 **인덱스 커버리지**다.
현재 Chroma 인덱스에는 개발셋 5개 법령의 해석례·판례만 적재돼 있고 홀드아웃 6개 법령은
하나도 없다. 뒤집어 말하면 **개발셋의 100%는 그 5개 법령용으로 맞춰 적재한 인덱스 위에서
나온 수치**이며, 임의의 법령을 조회하는 실사용 상황은 RAG 없이 돌아가는 홀드아웃 쪽에
가깝다. 인덱스를 넓히기 전까지 RAG 기여분을 성능으로 주장하지 않는다.

## 이 수치를 읽을 때의 주의

1. **applicability_v1은 개발셋이다.** 프롬프트를 이 셋의 오답을 보고 두 번 고쳤으므로
   그 100%는 낙관적으로 편향돼 있다. 일반화 성능을 말할 때는 **홀드아웃의 62.5%**를 쓴다.
2. **표본이 작다.** 개발셋 15건, 홀드아웃 16건. 케이스 1건이 6~7%p를 움직이므로
   신뢰구간을 논할 크기가 아니다. 홀드아웃의 HOLD 케이스는 2건뿐이라 보류 판정의
   정밀도는 사실상 측정되지 않았다.
3. **Q3는 대리 지표다.** 기획서의 Q3는 사용자가 실제로 행동했는지를 보는 제품 지표이고,
   여기서는 '해당 판정이 ACTION/DECISION으로 분류된 비율'로 근사했다.
4. **Q1은 두 값이다.** 사용자에게 노출되는 인용은 Validator 통과분이라 구조적으로
   100%다. 모델이 만든 인용 자체의 정확도가 그 아래 값이고, 둘의 차이가
   Validator가 막아낸 양이다.

## 정답 라벨 기준

`gold_applicability`는 **이 시스템이 주어진 입력으로 내려야 하는 판정**이다.
따라서 구체 기준이 하위법령에 위임된 조문은 HOLD가 정답이다 (BR-003).
라벨은 조문 원문을 직접 읽고 부여했으며, 근거를 각 케이스의 `note`에 적었다.

## 알려진 한계

근로기준법 제76조의2(직장 내 괴롭힘 금지)는 조문 문언에 규모 조건이 없지만 실제로는
5인 미만 사업장에 적용되지 않는다(시행령 별표1). 조문 단독 입력으로는 알 수 없으므로
4인 프로필 케이스를 평가셋에서 제외했다. 법률↔시행령 페어링이 붙으면 추가한다.

## 홀드아웃 운용 규칙

1. `holdout_v1`의 결과를 보고 프롬프트·룰을 고치지 않는다. 고치면 홀드아웃이 아니다.
2. 결함을 고칠 때는 개발셋(또는 새 개발셋)에서 고치고, **그 뒤에 홀드아웃을 다시 돌려**
   개선이 일반화됐는지 본다.
3. 홀드아웃을 여러 번 돌려 그 수치를 보고 의사결정을 반복하면 그 셋도 오염된다.
   `holdout_v1`을 두세 번 이상 의사결정에 쓰게 되면 `holdout_v2`를 새로 만든다.
4. 라벨은 실행 전에 확정한다. 결과를 보고 라벨을 바꾸지 않는다.
