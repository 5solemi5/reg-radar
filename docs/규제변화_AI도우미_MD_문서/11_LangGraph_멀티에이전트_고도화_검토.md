# 11. LangGraph 멀티에이전트 고도화 — 검토안

> **상태: 미구현 검토안 (2026-09-22).** 이 문서는 구현된 설계가 아니라 다음 단계
> 후보를 평가 실측에 근거해 정리한 것이다. 현재 코드에는 LangGraph가 없다
> (`backend/pyproject.toml`의 의존성은 `langchain` / `langchain-core` /
> `langchain-openai`뿐). 01 기획서·04 설계서의 확정 설계와 혼동하지 않도록,
> 여기서 제안한 항목은 실제로 구현할 때 해당 문서와 ADR에 옮겨 적는다.

## 11-0. 전제 — 왜 "에이전트를 여러 개"가 목표가 아닌가

현재 AI 파이프라인은 조문 1건당 **C3 추출 → C4 판정 → HOLD 정책(코드) →
C5 영향 → C6 검증**의 단일 경로다 (`backend/app/services/analysis_service.py`).
분기도 순환도 없다. 이 구조에서는 LangChain으로 충분했고, 실제로 그렇게 만들었다.

LangGraph가 주는 것은 에이전트의 **개수**가 아니라 지금 구조가 표현하지 못하는
세 가지다.

| 얻는 것 | 지금 없는 이유 | 해당 절 |
|---|---|---|
| **순환** — 판정이 미심쩍으면 되돌아가 다시 본다 | 선형 함수라 재시도 경로가 없다 | §11-1, §11-4 |
| **조건부 분기** — 판정 종류에 따라 다른 경로 | `if`가 늘어날수록 흐름이 안 보인다 | §11-1, §11-3 |
| **중단·재개** — 사용자 응답을 기다렸다 그 지점부터 | 보류는 별도 API 호출로 처리 중 | §11-5 |

따라서 이 검토의 판단 기준은 "에이전트를 몇 개로 쪼개는가"가 아니라
**"평가에서 미달인 지표가 움직이는가"**다.

## 11-1. Q4 재현율 66.7% → 과소판정 재심 루프 [우선순위 1]

### 현상

holdout_v3 18건(K01~K18) 기준 오답 3건이 **전부 같은 방향**이다.
(케이스 ID K로 시작하는 이 셋은 개발셋 applicability_v1(23건)이 아니라 세 번째 홀드아웃이다.)

| 케이스 | 정답 | 예측 | 상태 |
|---|---|---|---|
| K05 표시·광고의 공정화에 관한 법률 제3조 | APPLICABLE | NOT_APPLICABLE | VALIDATED |
| K11 정보통신망법 제45조 | APPLICABLE | NOT_APPLICABLE | VALIDATED |
| K12 정보통신망법 제45조 | HOLD | NOT_APPLICABLE | VALIDATED |

세 건 모두 `status=VALIDATED`로 Validator를 통과했다.

### 원인 — 게이트의 비대칭

`backend/app/validator/core.py:114`:

```python
substantiated = (
    applicability.applicability is not Applicability.APPLICABLE or bool(app_spans)
)
```

근거 없는 **"해당"은 REJECT**하지만, 근거 없는 **"무관"은 통과**한다. 이 설계는
의도된 것이다 — Q2(오탐)가 이 서비스에서 가장 위험한 출력이라고 보았고, 실제로
Q2는 0.0%를 달성했다. 그러나 그 대가로 누락만 한쪽으로 샌다. 사용자 관점에서는
"해당인데 무관이라 해서 안 챙긴 것"도 똑같이 손해다.

### 제안

무관 판정에만 거는 **비대칭 재심 루프**.

```
C4 판정
  └─ 조건부 엣지: NOT_APPLICABLE 인가?
       ├─ 예 → 반대심문 노드(적용된다고 볼 근거를 찾아보라)
       │        └─ C4 재판정 → 두 판정이 갈리면 HOLD로 내린다
       └─ 아니오 → C5로 진행
```

핵심은 재심 결과가 갈릴 때 **APPLICABLE로 올리지 않고 HOLD로 내리는 것**이다.
그래야 Q2 0%를 지키면서 Q4만 올린다. 보류 정밀도(현재 100%)는 일부 희생된다.

## 11-2. Q3 행동 전환 0% → 등급 산정을 LLM에서 분리 [우선순위 2]

### 현상

정답 APPLICABLE 4건 중 ACTION/DECISION 등급을 받은 것이 **0건**이다
(목표 ≥ 60%). "해당한다"고 판정해 놓고 사용자가 할 일은 제시하지 못한 셈이다.

### 원인

`backend/app/ai/chains/c5_impact.py`의 단일 호출이 요약·영향 업무·체크리스트·
행동 등급·등급 사유를 **한 번에** 생성한다. 서술 비중이 큰 출력에서 등급 같은
단일 레이블은 관성적으로 보수적인 값에 쏠린다.

### 제안

LangGraph 없이도 가능하다. 다만 노드 분리가 그래프에서 더 자연스럽다.

1. 영향 서술 노드 (요약 + 영향 업무)
2. 체크리스트 생성 노드 (기한·주체·산출물을 필드로 강제)
3. **등급 판정은 코드** — 체크리스트에 마감기한이 있는가 / 원문에 제재 조항이
   있는가 / 항목 수가 임계 이상인가로 규칙 산출

3번은 이미 쓰고 있는 원칙의 연장이다. AP-03에 따라 규모 기준을
`app/diff/headcount.py`가 계산해 사실로 주입하는 것과 같다.

## 11-3. RAG 커버리지 16.7% → agentic retrieval [우선순위 3]

18건 중 참고자료가 붙은 것은 3건뿐이다. `backend/app/rag/retriever.py`는
질의를 한 번 만들어 한 번 검색하고, `MIN_SCORE = 0.25` 미만이면 빈 목록을
돌려주고 끝난다. BR-005에 따라 0건은 정상 상태지만, **재시도해 본 0건**과
**한 번 해보고 만 0건**은 다르다.

검색 노드를 루프로 바꾼다.

```
검색 → 0건인가?
  ├─ 예 → 질의 재작성(법령명 제거, 업무 맥락 중심) → 재검색
  │        └─ 여전히 0건 → doc_types 확장(해석례 → 행정규칙·판례)
  │             └─ 최종 0건 승인 → NO_RAG_PLACEHOLDER
  └─ 아니오 → 진행
```

루프 상한 2회면 비용은 조문당 임베딩 호출 3회 이내로 묶인다.

## 11-4. REJECTED 재시도 경로 [우선순위 1 — 비용 대비 효과 최대]

`backend/app/ai/chains/base.py`와 `app/ai/llm.py`에 재시도 로직이 **한 줄도
없다**(`tenacity`를 의존성에 넣어두고 쓰지 않는다). Validator가 위조된 조문번호
때문에 REJECT하면 그 결과는 그대로 버려지고, 사용자에게는 결과 없음으로 보인다.

그래프에서는 `C6 → (fatal 실패인가?) → C4`로 되돌아가는 엣지와 state의
`retry_count` 필드면 끝난다. 실패 사유(`ValidationReport.failures`)를 프롬프트에
되먹이면 같은 위조를 반복할 확률도 낮아진다. 상한 2회.

## 11-5. HOLD 중단·재개 [우선순위 4]

위임 케이스의 보류율이 27.8%다. 보류 사유가 "프로필에 없는 정보"일 때 현재는
결과를 일단 내보내고 사용자가 `reassess`를 별도로 호출한다.

LangGraph의 `interrupt` + checkpointer는 이 용도로 설계된 기능이다. 그래프가
보류 지점에서 멈춰 대기하다가 답이 오면 그 노드부터 재개한다. 다만
`app/services/reassess_service.py`가 이미 이 일을 하고 있고, BR-008(기존 결과를
덮어쓰지 않고 이력으로 연결)까지 지킨다. 얻는 것은 새 기능이 아니라 코드 통합
뿐이므로 우선순위는 낮다.

## 11-6. 부수 효과 — 관측과 시각화

- `graph.get_graph().draw_mermaid_png()`로 파이프라인 다이어그램이 코드에서
  자동 생성된다. 현재 `docs/diagrams/기능_흐름도.svg`는 손으로 그린 것이라
  코드와 어긋날 수 있다.
- LangSmith 연동이 환경변수 3개로 붙는다. 01 기획서 §265와 04 설계서 §213이
  Observability를 "LangSmith 또는 Langfuse / 필수"로 적어 두었으나 실제 구현은
  자체 trace 테이블 + `backend/scripts/trace_report.py`(CLI)로 갔다. 이 문서와
  구현의 불일치가 함께 해소된다. **LangGraph를 도입하지 않기로 하더라도 이
  불일치는 별도로 정리해야 한다** — 설계서 쪽을 실제 구현에 맞춰 고치는 편이
  작업량이 작다.

## 11-7. 대가

### 지연 (NFR-006)

현재 조문 1건당 latency p50 5,901ms · p95 13,950ms. ADR-016에서 동시성 4 +
분석당 조문 12건 상한으로 전체를 42초까지 줄여놓은 상태다.

재심 루프는 조문당 LLM 호출을 3회에서 최대 5~6회로 늘린다. 그대로 두면
NFR-006을 다시 위반한다. 예산 설계가 함께 필요하다.

- 재심은 **무관 판정에만** 건다 (전체가 아니라 일부에만 추가 비용)
- 조문 상한을 12건 → 8건으로 낮추는 안을 함께 검토
- 루프 상한을 state에 명시하고 초과 시 HOLD로 종료

### 결정론적 게이트가 희석될 위험

이 시스템의 방어선은 LLM 위에 얹은 코드 게이트다 — Validator(`app/validator/`,
테스트 19개로 고정), `deterministic_hold_reasons`(AP-03, AP-04, BR-003),
`headcount.evaluate`. Q2 오탐 0.0%와 Q6 금지 필드 유출 0건은 이 게이트의
결과지 모델의 미덕이 아니다.

에이전트를 늘리면서 판정 권한을 LLM으로 되돌리면 이 수치가 먼저 깨진다.
도입한다면 원칙을 하나 고정해 두어야 한다.

> **에이전트는 증거 수집과 재심까지, 확정은 코드가 한다.**

| 단계 | 내용 | 기대 효과 | LangGraph 필요 |

## 11-9. 수치의 한계

이 문서가 인용한 실측값은 모두
`backend/evaluation/results/20260921T105741Z_gpt-4o_rag.txt` 기준이다.

- **holdout_v3 18건**이다. 홀드아웃 셋은 3개(holdout_v1·v2·v3) 있으며, 이 측정에 쓰이면서 v3도 튜닝에 노출됐다.
  표본이 작고, 이후 수치는 새 봉인셋에서 다시 재야 한다.
- 오답 3건 중 2건이 같은 조문(정보통신망법 제45조)이다. 표본이 작아 Q4의
  66.7%는 케이스 몇 건에 크게 흔들린다.
- 목표값(Q1~Q6)은 01 기획서 §11의 **설계 목표**이지 달성 보증이 아니다.
- 따라서 위 우선순위는 현재 데이터에서의 판단이며, 케이스를 늘려 재측정한 뒤
  다시 보아야 한다.
