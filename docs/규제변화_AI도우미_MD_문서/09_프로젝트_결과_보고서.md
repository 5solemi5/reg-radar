## 2. 핵심 설계 — 신뢰성을 구조로 만들었다

이 프로젝트의 차별점은 기능 개수가 아니라 **"AI가 지어내지 못하게 만든 방식"**이다.
프롬프트로 부탁하지 않고 타입·스키마·제약·검증으로 막았다.

### 2-1. 담을 자리를 없앴다

LLM 출력 스키마에 `law_name`, `article_no`, `effective_date` 필드가 **존재하지
않는다**. 모델이 법령 사실을 위조하려 해도 넣을 자리가 없다. `extra="forbid"`라
끼워 넣으려 해도 파싱에서 거부된다.

```python
FORBIDDEN_FACT_FIELDS = {"law_id", "law_name", "article_no", ...}

def assert_no_forbidden_fields(model):  # 테스트가 회귀를 고정한다
    leaked = FORBIDDEN_FACT_FIELDS & set(model.model_fields)
```

### 2-2. 자유 서술에 숨어든 위조도 잡는다

스키마를 막아도 모델은 `reason` 안에 "제99조에 따라"라고 쓸 수 있다. Validator가
AI 서술에 등장한 **조문번호·날짜·참고자료 인용**을 근거 범위와 대조해, 범위 밖이면
결과를 거부한다.

### 2-3. 인용을 원문과 대조한다

AI가 제시한 인용이 실제 조문에 존재하는 문자열인지 substring으로 확인한다.
확인되지 않으면 제거하고, **검증된 근거가 하나도 남지 않은 "해당" 판정은 거부**한다.
근거 없는 확정이 이 서비스에서 가장 위험한 출력이기 때문이다.

### 2-4. 네 겹으로 막았다

| 계층 | 막는 것 |
|---|---|
| 출력 스키마 | 사실 필드 부재, HOLD의 missing_context 필수 |
| Validator | 인용 미검증, 조문번호·날짜 위조, 없는 출처 인용 |
| DB 제약 | 보류에 행동등급 부여, 사용자당 진행 중 분석 중복 |
| 화면 | 법적 근거 / 참고자료 / AI 해석을 배지로 분리 |

같은 규칙을 여러 계층에서 막는다. 한 겹이 뚫려도 다음 겹이 잡는다.

보류**는 틀린 인용도 오탐도 누락도 아니라 어디에도 잡히지 않았다. 지표 집합 자체에
구멍이 있었다. 원인과 조치는 §6-1에 있다.

## 4. 기술적 문제와 해결

실제로 겪고 고친 것만 적는다. 대부분 **코드를 짤 때가 아니라 실제 데이터로 돌려볼 때**
드러났다.

### 4-1. 산술을 LLM에 맡겨 서비스가 무용지물이 됐다

첫 E2E에서 세 프로필이 **전부 보류**로 나왔다. 오탐은 0%였지만 아무것도 판단해
주지 않는 서비스였다. 원인은 모델이 *"상시 10명 이상의 정의가 필요합니다"* 라며
**80명 vs 10명이라는 산술 비교를 판단 불가로 취급**한 것이었다.

산술은 의미 해석이 아니므로 코드로 옮겼다(`app/diff/headcount.py`). 조문에서 수치
기준을 정규식으로 뽑아 사용자 인원과 비교한 뒤 *"코드가 계산한 사실 — 재검토 대상
아님"* 으로 프롬프트에 주입한다.

| 프로필 | 수정 전 | 수정 후 |
|---|---|---|
| 4인 쇼핑몰 | 보류 | **무관** (10명 미만) |
| 80인 IT HR | 보류 | **해당 · 조치 필요** |
| 인원 미입력 | 보류 | 보류 (상시근로자 수 요청) |

### 4-2. 판정 순서가 거꾸로였다

평가 첫 실행이 **정확도 46.7%, 과도한 보류율 70%** 였다. IT 서비스 회사가
"유해화학물질 영업자"인지는 물어볼 것도 없이 무관인데, 조문에 위임 문구가 있다는
이유로 보류가 나왔다.

C4 프롬프트를 **"대상 집단 확인 → 세부 기준 확인"** 2단계로 고정했다. 대상이
아니면 위임된 기준이 무엇이든 무관이다.

**46.7% → 80.0% → 86.7%**, 과도한 보류율 **70% → 0%**.

다만 3회차 수정에서 **Q4 재현율이 80%→60%로 악화**했다. 보류가 사라진 만큼
"무관"으로 흘러간 것이고, 임계값이 이동했을 뿐 능력이 오른 게 아니다. 같은 셋에
세 번째로 맞추는 것은 과적합이라 **튜닝을 중단**하고 모델을 바꿔 원인을 분리했다.

### 4-3. 분석 대상 선정이 없었다

"최근 규제 변화를 분석한다"의 대상이 미정의 상태였다. 근로기준법 한 건이 132개
조문이라 전량 투입은 불가능하고, 조문별 시행일자는 개정 여부와 무관하게 전부 법령
시행일자로 채워져 신호로 쓸 수 없었다.

**법제처 신구법 비교 API**가 두 문제를 함께 풀었다. 변경 조문만 반환하고, 바뀐
구간을 `<P>` 태그로 직접 표시한다.

```
근로기준법 전체 132개 조문 중 이번 개정에서 변경된 조문: 제60조 1건
  − 제19조제1항에 따른
  + 제19조에 따른
```

**변경점을 추정할 필요가 없어졌다.** 우리 diff 알고리즘조차 개입하지 않는다.

### 4-4. 관심 영역을 수집만 하고 쓰지 않았다

화면을 붙이고 나서야 드러났다. 최신순 3건을 집었더니 IT HR 담당자에게
'감사원사무처 직제', '하천법 시행규칙'이 분석 대상으로 나왔다. 판정은 정확히
'무관'이었으나 볼 필요 없는 것에 비용만 썼다.

프로필의 `interests`는 기획서 §9에 "개인화 기준"으로 정의됐는데 한 번도 쓰이지
않고 있었다. 관심영역·업종을 법령명 검색어로 바꾸도록 고쳤다.

### 4-5. 분석이 3분을 넘겼다

조문 1건이 LLM 3회를 쓰는데 순차로 돌고 있었다. 동시성 4 + 분석당 조문 12건 상한으로
**181초 초과 → 42초**. 법령을 번갈아 뽑아 한 법령이 상한을 독식하지 않게 했다.

### 4-6. 실제 데이터에서만 드러난 것들

| 문제 | 원인 | 해결 |
|---|---|---|
| 장 제목이 조문으로 섞임 | 법제처가 `제1장 총칙`도 `<조문단위>`로 주고 **뒤 조문과 번호를 공유** | 조문 목록에서 제외하고 chapter 메타로 보존 |
| CHECK 제약이 통과됨 | `array_length(빈 배열)`은 0이 아니라 **NULL**이고 CHECK는 NULL이면 통과 | `cardinality()`로 교체 |
| 확신도가 0.9→0.8999… | `real`(float4) 정밀도 손실 | `double precision` |
| jsonb가 str로 돌아옴 | 코덱 설치 후 `json.dumps`로 이중 인코딩 | dict를 그대로 전달 |
| RAG가 관련 판례를 전부 걸러냄 | 법령 API는 `개인정보 보호법`, 판례는 `개인정보보호법위반` — **띄어쓰기** | 공백 무시 비교 |
| 인증 토큰을 거부 | Supabase 현재 키가 **ES256 비대칭**인데 HS256 전제로 구현 | JWKS 공개키 검증 |
| CORS 환경변수 파싱 실패 | pydantic-settings가 validator보다 **먼저** JSON 파싱 시도 | `NoDecode` |

## 5. 과정에서 배운 것

**실제 데이터로 돌려보기 전에는 모른다.** 위 문제의 대부분은 코드 리뷰나 단위
테스트로는 보이지 않았다. 법제처 실응답을 파싱하고, 스키마를 실제 DB에 적용하고,
컨테이너를 띄우고, 화면을 그리고 나서야 드러났다.

**같은 테스트를 두 구현에 돌리면 차이가 드러난다.** 저장소 계약 테스트를 인메모리와
Postgres 양쪽에 돌려 세 건의 버그를 잡았다.

**문서는 그냥 두면 낡는다.** OpenAPI와 명세서를 대조하는 테스트를 넣었더니, 실제로
엔드포인트를 추가하고 문서를 안 고쳤을 때 테스트가 깨져 잡혔다.

**지표 하나만 보면 다른 쪽이 망가진다.** 보류율을 0%로 만들자 재현율이 떨어졌다.
Q2(오탐)와 과도한 보류율은 서로를 잡아먹으므로 함께 봐야 한다.

## 6. 한계 — 정직하게

### 6-1. 홀드아웃을 만들었더니 100%가 62.5%였다

개발셋 100%가 과적합인지 확인하려고, 프롬프트 수정에 **한 번도 쓰지 않은** 16케이스를
만들어 **한 번만** 돌리고 그 수치를 그대로 기록했다. 법령은 개발셋과 겹치지 않고,
프로필 2종을 새로 넣었으며, 라벨은 실행 전에 확정했다.

**1차 결과는 62.5%.** 개발셋 수치는 일반화되지 않았다.

**오답 6건이 전부 같은 결함이었다.** 6건 모두 `→ HOLD`이고 위임 유무로 정확히 갈린다.

| 조문 특성 | 케이스 | 정확도 |
|---|---|---|
| 위임 문구 **없음** | 6건 | **100%** (6/6) |
| 위임 문구 **있음** | 10건 | **40%** (4/10) |

위임이 있으면서 정답이 APPLICABLE인 5건은 5건 모두 HOLD로 갔다. **ADR-011("적용을
가르는 핵심 기준이 위임되면 보류")을 조건부 원칙이 아니라 무조건 규칙으로 적용하고
있다.** 최저임금법 제6조의 위임은 *산입 임금의 범위*에 관한 것이지 최저임금 지급 의무
자체를 좌우하지 않는데도 보류가 나왔다. 사용자에게 "최저임금을 줘야 하는지 모르겠다"고
답하는 셈이다.

**왜 개발셋에서는 안 보였나.** 개발셋에는 `위임 있음 + 정답 APPLICABLE` 패턴이 사실상
없었다. §5의 3회차 프롬프트 수정은 개발셋의 **반대 방향** 오답(위임 있음 + 정답
NOT_APPLICABLE)만 보고 이뤄졌다. 경계를 한쪽으로 밀어 그 셋의 오답을 없앴고, 그 셋에는
반대편 케이스가 없어서 100%가 나왔다. 46.7%→86.7%의 개선 중 일부는 능력 향상이지만
**일부는 임계값 이동이었다.** §5에서 "Q4 재현율이 80%→60%로 악화했다"며 이미 의심했던
현상이 홀드아웃에서 수치로 확인된 것이다.

**진짜 원인은 프롬프트가 아니라 코드였다.** `deterministic_hold_reasons`가 위임 문구만
있으면 LLM 판정과 무관하게 보류로 강등하고 있었다. 프롬프트는 이미 "부수적 위임은
보류 사유가 아니다"라고 쓰고 있었는데 코드가 그 위에서 덮어썼다. 프롬프트만 들여다봤으면
못 찾았을 결함이다.

### 6-1-1. 고친 방법 — 법률↔시행령 페어링 (ADR-025~027)

위임된 하위법령 조문을 찾아 근거로 함께 준다. 시행령 조문이 "법 제6조제4항에 따라"로
모법을 직접 참조하므로 역매핑이 가능하다 — 추론이 아니라 원문에 적힌 사실이다.
강등 조건도 '위임이 있는가'에서 **'기준을 손에 넣었는가'**로 바꿨다.

| | 개발셋 | 홀드아웃 1차 | 홀드아웃 2차 |
|---|---|---|---|
| 판정 정확도 | 100% (유지) | 62.5% | **100%** |
| 과도한 보류율 | 0% (유지) | 42.9% | **0%** |
| 위임 케이스의 보류율 | 50% | 100% | **10%** |

**만들면서 세 번 조였고, 세 번 다 실제 법령에서 틀린 뒤에 알았다.**

| 문제 | 증상 | 조치 |
|---|---|---|
| 타법 참조를 모법으로 오인 | 시행령의 "근로기준법 제50조"를 모법 제50조로 색인 | 앞 글자가 한글이면 제외 |
| 스쳐가는 참조를 이행 조문으로 오인 | 개인정보 보호법 제31조에 무관한 시행령 조문 3건이 근거로 붙음 | 각 항의 **근거 절**에서만 인정 (ADR-026) |
| 재위임을 해소로 오인 | 산안법 시행령 제16조 "별표 3과 같다"를 붙였더니 150인 제조업이 **무관**으로 판정 | 맨 앞 이행 조문이 기준을 담을 때만 보류 해제 (ADR-027) |

마지막 것이 가장 위험했다. 보류가 무관으로 바뀌는 것은 개선이 아니라 **더 나쁜 실패**다.
'관련 규제를 놓치는 쪽이 보류보다 나쁘다'(NFR-003)는 원칙이 없었으면 "보류율이 줄었다"고
자축했을 수치다.

같은 버그를 두 번 밟은 것도 확인했다. `정하`가 `정한다`에 매치되지 않는 한국어 활용
문제를 diff 엔진에서 이미 고쳤는데 페어링 모듈에서 똑같이 재현했다. 활용형 패턴을
`DELEGATION_VERB` 공개 상수로 올려 두 곳이 같이 쓰게 했다.

### 6-1-2. 그래서 이 100%는 무엇을 뜻하나

**깨끗한 홀드아웃 수치가 아니다.** 프롬프트·룰을 홀드아웃 결과에 맞춰 조정하지는
않았고 수정은 전부 개발셋에서 검증했지만, *무엇을 고칠지*는 홀드아웃의 실패 양상을
보고 알았다. 그 정보가 설계에 들어간 이상 이 16건은 더 이상 미지의 데이터가 아니다.

`holdout_v1`은 세 번 실행됐다(진단 1회, 수정 확인 1회, 정규식 버그 수정 후 재확인 1회).
운용 규칙상 **튜닝 목적으로는 소진**됐고, 다음 일반화 주장에는 `holdout_v2`가 필요하다.

이 100%가 뒷받침하는 것은 "62.5%를 만든 결함이 실제로 고쳐졌고 개발셋을 망가뜨리지
않았다"까지다. "이 시스템의 일반화 정확도가 100%"가 아니다.

**남은 한계.** 표본이 15~16건이라 케이스 1건이 6~7%p를 움직인다. 홀드아웃의 HOLD
케이스는 2건뿐이라 보류 판정의 *정밀도*는 사실상 측정되지 않았다.

### 6-1-3. 두 번째 홀드아웃이 알려준 것 — 보류 재현율 40%

`holdout_v1`이 소진되어 겹치지 않는 법령 10개로 `holdout_v2`(22케이스)를 만들었다.
v1의 약점 둘을 메우는 것이 목적이었다 — HOLD 케이스가 2건뿐이라 보류 정밀도·재현율을
못 쟀던 것, 그리고 페어링이 처음 보는 법령에서도 되는지 확인 못 한 것이다.

**v1의 100%는 역시 낙관적이었다. v2 1차는 68.2%.** 오답 7건 중 5건이 또
`APPLICABLE → HOLD`였다. 위임 조문은 100% 확보했는데도 보류가 났다 — ADR-027을 조문
**전체**에 적용한 탓에, 호·목 안의 무관한 별표 참조 하나 때문에 기준을 제대로 담은
조문까지 '미해소'로 잡힌 것이다. 위임을 이행하는 문장 안에서만 판단하도록 고쳐
(ADR-030) 86.4%가 됐다.

고치는 중에 `holdout_v1`이 100% → 93.8%로 회귀했다. **회귀를 잡아준 것이 이미
소진된 v1이다.** 소진된 홀드아웃도 회귀 검사로는 계속 값지다.

#### 정확도보다 중요한 발견

정확도는 올랐지만 보류 재현율은 40%(5건 중 2건) 그대로다. 잡은 것과 놓친 것의
성격이 정확히 갈린다.

| 유형 | 결과 | 누가 판단하나 |
|---|---|---|
| 상시근로자 수 미상 | **2/2 잡음** | 결정적 계층(`headcount.py`)이 강제 |
| 사업 형태 미상 | **0/3 놓침** | LLM에 맡겨져 있고, 모르면 추측한다 |

하도급법 제3조는 '원사업자'가 대상인데 프로필에 위탁 여부가 없고, 전자상거래법
제17조는 '통신판매업자'가 대상인데 통신판매 여부가 없다. 시스템은 업종만 보고
제조업이면 해당, IT 서비스면 무관으로 단정했다.

**결정적 계층이 아는 미지수는 상시근로자 수 하나뿐이다.** AP-03("산술은 코드가")을
규모에만 적용했고, '이 사용자가 대상 집단인지 판단할 정보가 있는가'는 계층으로
만들지 않았다. 보류 정밀도 100%는 그 눌림의 부산물이다 — 프롬프트가 "보류를 남용하지
마십시오"로 강하게 눌러 헛보류는 없지만 놓치는 쪽으로 치우쳤다.

**고치지 않고 남겼다.** v2를 세 번째로 쓰면 소진되므로, 다음 사이클에서 개발셋으로
고치고 `holdout_v3`로 확인한다.

#### 평가 방법론 자체의 한계

v1(3회)·v2(2회) 모두 소진됐다. 매번 '진단 → 수정 → 확인'에 홀드아웃 한 셋이 쓰인다.
근본 해법은 케이스 풀을 크게 만들어 두고 일부를 끝까지 손대지 않는 것인데, 케이스마다
조문 원문을 읽고 라벨을 붙여야 해서 규모를 키우는 비용이 크다. 지금 인용할 수 있는
가장 보수적인 일반화 수치는 **v2 1차의 68.2%**(어떤 수정도 반영되기 전)이다.

### 6-1-4. 세 번의 홀드아웃이 말해 준 것 — 실제 일반화는 65% 근처다

가장 중요한 수치는 개별 셋의 최종값이 아니라 **세 셋의 1차 실측**이다.

| 데이터셋 | 법령 | 1차(수정 전) | 최종 |
|---|---|---|---|
| `holdout_v1` (16케이스) | 6개 | **62.5%** | 100% |
| `holdout_v2` (22케이스) | 10개 | **68.2%** | 90.9% |
| `holdout_v3` (18케이스) | 7개 | **66.7%** | 83.3% |
| | | **평균 65.8%** | |

세 셋은 법령이 서로 겹치지 않고, 만들어질 때 시스템이 그 내용을 본 적이 없었다.
그런데 **1차 실측이 62~68%로 사실상 같다.** 케이스 하나가 4~6%p를 움직이는 표본
크기를 감안하면 같은 값을 세 번 잰 것이다.

**따라서 처음 보는 법령에 대한 실제 기대치는 65% 근처다.** 수정 후의 83~100%는
*그 셋이 드러낸 결함을 고친 뒤의 그 셋에 대한 수치*이지 다음 법령에 대한 예측이
아니다. 매 사이클이 그것을 보여줬다 — v1을 100%로 만든 뒤 v2는 68.2%로 시작했고,
v2를 90.9%로 만든 뒤 v3는 66.7%로 시작했다.

**나쁜 소식만은 아니다.** 세 사이클이 고친 결함은 서로 달랐고 전부 실재했으며,
앞 사이클이 고친 것은 뒤 셋에서 재발하지 않았다. 개선은 누적되고 있다. 다만 매번
**새로운 종류의** 실패가 나온다 — 법령이 많고 각각이 새로운 판정 축을 요구하기 때문이다.

> **보고 원칙:** 일반화 수치로는 **약 65%**(세 홀드아웃 1차 평균)를 쓴다. 최종 수치는
> "이 결함들을 고쳤다"의 근거이지 성능 주장이 아니다. 최종 수치만 떼어 "정확도 90%"라고
> 말하면 과장이다.

### 6-1-4-1. 세 번째 사이클에서 고친 것 — 근거 없는 '무관' 확정

v2가 남긴 보류 재현율 40%를 고쳤다. 놓친 3건이 전부 '사업 형태 미상' 유형이었고
개발셋에는 그 유형이 한 건도 없어, 먼저 개발셋을 넓혔다(E16~E19, 도급 관련 4건).

모델에게 묻는 질문을 바꾼 것이 핵심이다 — **'적용되는가'가 아니라 '판단할 근거가
프로필에 있는가'**. 근거가 없으면 코드가 보류로 내린다(ADR-031). 위임·규모 사유와
달리 이 사유는 **무관도 강등**한다. 대상인지 모르는데 '무관'이라고 말하는 것은
근거 없는 확정이기 때문이다.

개발셋은 84.2% → 100%가 됐다. **그런데 `holdout_v3`는 66.7%였다.**

오답 6건이 전부 무관 확정이었고, 모델에게 근거를 직접 물어보니 이렇게 답했다.

> "업종이 IT 서비스로, 정보통신서비스 제공자에 해당하지 않는다"
> "IT 서비스 업종의 **HR 담당자**는 '사업자등'에 해당되지 않습니다"

둘 다 명백한 오답이고 원인이 둘이었다.

1. **`profile_excludes`가 검증 불가능한 주장이었다.** 개발셋의 새 케이스는 전부
   '도급' 유형이라 인허가와 무관했고, 그래서 "인허가가 필요한 업종인가"라는 내
   판단 기준이 개발셋에서 한 번도 시험되지 않았다. 전형적인 과적합이다.
2. **판정 주체를 혼동했다.** 조문이 적용되는 상대는 회사인데 모델이 'HR 담당자'라는
   개인을 보고 판단했다. 프로필에 직무가 있어서 생긴 혼동이다.

**조문 인용에서 이미 배운 것을 프로필 판단에 옮겨 고쳤다**(ADR-032). 모델은
`profile_evidence`에 프로필 한 줄을 그대로 복사해야 하고, 실제 프로필에 없으면 판단이
버려져 보류로 내려간다. 요구만 하고 대조하지 않으면 모델은 그럴듯한 문장을 지어낸다 —
이 프로젝트가 FR-021에서 이미 겪은 일이다.

`holdout_v3` 66.7% → 83.3%, 보류 재현율 33% → 83%. 개발셋·v1 회귀 없음, v2는 86.4% →
90.9%로 개선.

남은 오답 3건은 **검증으로 잡을 수 없는 종류**다. 셋 다 `- 업종: IT 서비스`처럼
실재하는 프로필 줄을 근거로 대고 거기서 틀린 결론을 끌어냈다. 인용 검증은 '그 줄이
있는가'만 보지 '그 줄이 그 결론을 뒷받침하는가'는 보지 못한다. 근거 조작은 막았지만
근거 해석은 여전히 LLM의 몫이다.

### 6-1-5. 병목은 판정 능력이 아니라 입력 설계였다

홀드아웃 세 셋에서 놓친 보류가 전부 같은 유형이었다. 조문은 명확한데 '이 회사가
도급을 주는가', '외국인근로자를 고용하는가'를 프로필이 말해 주지 않아 판정할 수
없었다. 모델을 더 좋게 만들어도 없는 정보는 만들어지지 않는다.

그래서 **질문 8개를 온보딩에 넣었다**(ADR-033). 목록은 실제 평가에서 보류를 만든
조문에서 역산했다 — 짐작으로 늘리지 않는다.

같은 조문·같은 회사인데 답만 달리해 측정했다.

| 케이스 | 사업 활동 응답 | 판정 |
|---|---|---|
| 근로기준법 제44조 (도급 사업 임금) | **모름** | HOLD |
| 〃 | **예** | APPLICABLE |
| 〃 | **아니오** | NOT_APPLICABLE |

산업안전보건법 제63조(도급인의 안전조치)도 같았다. 개발셋 23케이스 기준 판정
정확도 100%, 보류 재현율 100%, 보류 정밀도 100%, 과도한 보류율 0%.

**`아니오`와 `모름`을 구분한 것이 핵심이다**(ADR-034). 체크박스 하나로 받으면 체크하지
않은 것이 '아니오'인지 '아직 답하지 않음'인지 알 수 없고, 그러면 질문을 건너뛴
사용자에게 '무관'이라고 단정하게 된다 — §6-1-3에서 고친 실수를 입력 단계에서 그대로
반복하는 셈이다. 프롬프트에도 답하지 않은 항목을 `모름 (사용자가 답하지 않음)`으로
**항상 적는다.** 줄을 빼면 모델이 없는 줄을 '아니오'로 읽는다.

질문 문구는 백엔드가 유일한 출처이고 `GET /profile/activities`로 내보낸다. 프론트가
같은 목록을 따로 들고 있으면 반드시 어긋나고, 항목이 하나 빠져도 아무도 모르는 채
사용자는 답할 기회조차 없는 질문 때문에 보류를 받는다.

| 문제 | 원인 |
|---|---|
| E2E가 낡은 백엔드를 테스트하고 있었다 | Playwright에 `webServer` 설정이 없어 수동으로 띄운 프로세스를 쓴다. 몇 시간 전 프로세스가 살아 있었다. 이번엔 응답 스키마가 바뀌어 Zod가 잡았지만, 동작만 바뀌었다면 낡은 코드에 초록불이 떴을 것이다 → 사전 점검에 버전 확인 추가 |
| 일일 한도가 E2E를 막았다 | 비용 상한 기본값 10이 로컬 개발까지 묶었다 → 기본 0(무제한), 운영에서는 값을 반드시 지정하게 가드 추가 |
| 재판정 E2E가 조용히 건너뛰어졌다 | 보류 결과가 없으면 `test.skip`. 살아 있는 법제처 데이터에 의존했다 → 법령을 차례로 시도하고 그래도 없으면 실패 |
| 스크린리더가 질문을 세 번 읽었다 | `legend` + 문단 + `aria-label`에 같은 문장 → 한 번만 쓰고 `aria-labelledby`로 가리킴 |

두 번째가 특히 시사적이다. **안전한 기본값에 기대면 설정을 빠뜨렸는지 일부러 껐는지
구분되지 않는다.** 기본을 끄고 운영에서 기동을 막는 편이 낫다.

### 6-2. RAG의 효과를 측정하지 못했다

RAG 켬/끔으로 정확도는 양쪽 100%로 같았다. 당연한 결과다 — 적용 여부는 조문 문언과
규모 계산이 결정하고 둘 다 결정적 계층이 담당한다. RAG의 가치는 **설명의 질**에
있는데 Q1~Q6는 그것을 측정하지 않는다.

의미 있는 결과는 **참고자료 73건을 추가로 넣고도 Q6이 0건을 유지**했다는 것이다.
컨텍스트가 늘면 환각도 느는 것이 일반적인데 Validator와 프롬프트 경계가 버텼다.

**홀드아웃에서 더 불편한 사실이 나왔다.** 같은 `--rag` 옵션으로 돌렸는데 16케이스 전부
참고자료가 **0건** 검색됐다. 버그가 아니라 인덱스 커버리지다 — 현재 인덱스에는 개발셋
5개 법령의 해석례·판례만 적재돼 있다. 뒤집어 말하면 위의 "RAG 켬" 수치는 **그 5개
법령용으로 맞춰 적재한 인덱스 위에서 나온 값**이고, 임의의 법령을 조회하는 실사용
상황은 오히려 RAG 없이 돌아간 홀드아웃 쪽에 가깝다. 인덱스를 넓히기 전까지 RAG
기여분을 성능으로 주장하지 않는다.

### 6-3. 위임 조항이 많은 법에서 보류율이 높다

개인정보보호법·산업안전보건법 실측에서 12건 중 9건이 보류였다. 구체 기준이
하위법령에 있으면 설계상 보류가 맞지만, 사용자에게는 보류가 많아 보인다.
**법률↔시행령 페어링**이 근본 해법이나 미구현이다.

### 6-4. 조문 단독 판단의 한계

근로기준법 제76조의2(직장 내 괴롭힘 금지)는 문언에 규모 조건이 없지만 시행령
별표1이 5인 미만 사업장을 제외한다. 조문만 보면 알 수 없다.

### 6-5. 미구현

| 항목 | 상태 |
|---|---|
| UC-11 분석 이력 비교 | **미구현.** 이력 조회는 되지만 두 분석을 나란히 비교하는 화면이 없다 |
| 별표 조회 | **미구현.** 기준이 별표에 있으면 페어링 뒤에도 보류로 남는다 (ADR-027) |
| RAG 인덱스 커버리지 | **개발셋 5개 법령뿐.** 그 밖에서는 검색 0건이다 (§6-2) |
| RAG 품질 평가셋 | 미구현. 참고자료가 유용한지 아직 측정하지 못했다 |
| Pinecone 전환 | 미구현 (Protocol은 준비) |
| 보도자료 수집 | 법제처에 해당 target 없음 |
| CI/CD | 미구성. 수동 배포 |
| 스테이징 환경 | 미분리. local과 production만 |

**완료된 것** (이 표에 한때 '미구현'으로 적혀 있었다):
법률↔시행령 페어링(ADR-025~030), 대상 집단 판단 계층(ADR-031~032),
프로필 사업 활동(ADR-033~034), 실제 배포(§1-3).

> 이 표가 한동안 낡은 채로 있었다. "남은 일이 뭐냐"는 질문에 문서가 틀린 답을
> 주고 있었던 셈이다. 자동 문서 동기화 테스트는 **API 엔드포인트와 수치**는
> 잡지만 이런 서술형 상태는 잡지 못한다. 기능을 끝낼 때 이 표를 함께 고친다.

### 6-3. 배포 설정은 문법만 맞았다

배포 전 점검에서 컨테이너를 실제로 띄워 보니 세 가지가 나왔다. 셋 다 로컬
`uvicorn`으로는 드러나지 않는다.

| 문제 | 증상 | 원인 |
|---|---|---|
| 마이그레이션이 영영 안 돈다 | 없음 (조용히 건너뜀) | Railway는 Dockerfile 빌더에서 `Procfile`을 읽지 않는데 `release:` 단계만 믿었다 |
| `preDeployCommand`가 매번 실패 | `ModuleNotFoundError: No module named 'app'` | 의존성 캐시용으로 `pyproject.toml`만 먼저 복사해 설치해서 패키지 본체가 설치되지 않았다. `uvicorn`은 작업 디렉터리 덕에 우연히 동작했다 |
| 운영에서 RAG가 조용히 꺼짐 | `rag_enabled: true, 청크 0` | `chromadb`가 의존성에 선언조차 안 돼 있었다. 로컬 venv에만 있었다 |

세 번째는 **헬스체크가 오히려 오해를 키웠다.** '청크 0건'은 인덱스가 빈 것과
라이브러리가 없는 것을 구분하지 못해, 운영자는 적재만 하면 되는 줄 알게 된다.
`rag_operational`과 `rag_error`를 나눠 원인을 말하도록 고쳤다.

**§5의 교훈이 배포 단계에서 다시 반복됐다** — 실제로 실행해 보기 전에는 모른다.
문서와 설정 파일이 문법적으로 맞다는 것과 동작한다는 것은 다른 얘기다.
그래서 08 가이드 §6-4에 '컨테이너에서 한 번은 돌려 본다'를 점검 항목으로 넣었다.
