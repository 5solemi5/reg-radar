# 07. RAG 설계서

기획서 §7의 Hybrid RAG 전략을 실제 파이프라인으로 구현한 기록이다. 설계안이
아니라 동작하는 구현의 기록이며, `backend/app/rag/`가 기준이다.

문서 상태: W5 구현 완료 기준 · 작성 기준일: 2026-09-21
상위 문서: 01 기획서 §7 / 04 시스템 아키텍처 설계서

---

## 1. RAG가 하는 일과 하지 않는 일

> **원칙 (기획서 §7):** RAG는 법령 원문을 대체하지 않는다. **법적 근거는 법제처
> 조문 API**, RAG는 법령만으로 부족한 **실무 맥락**을 보강한다.

| | 법적 근거 | 참고 자료 (RAG) |
|---|---|---|
| 출처 | 법제처 조문 API | 법제처 법령해석례·행정규칙·판례 |
| 성격 | 공식 사실값 | 실무 맥락 |
| 검증 | 인용이 원문에 존재하는지 대조 (FR-021) | 출처 metadata 필수 (FR-013) |
| 없을 때 | 분석 불가 | **정상 상태** (BR-005) |
| 화면 | `legal_evidence` | `reference_evidence` |

**섞이지 않도록 타입부터 분리했다.** `RagContext`에는 `law_name`, `article_no`,
`effective_date`, `original_text` 필드가 **존재하지 않는다.** 참고자료가 법적
근거인 척할 수 있는 자리가 없다 (BR-004).

---

## 2. 데이터 소스 — 법제처를 쓴 이유

기획서는 "정부 가이드·FAQ·행정해석·보도자료"를 RAG 대상으로 정의했다. 정부
사이트를 스크래핑하는 대신 **법제처 OPEN API의 다른 target**을 쓴다.

| 기획서의 문서 유형 | 법제처 target | 실제 내용 |
|---|---|---|
| FAQ·행정해석 | `expc` 법령해석례 | 질의요지 / 회답 / 이유 구조 |
| 정부기관 가이드 | `admrul` 행정규칙 | 훈령·예규·고시 조문 |
| 검증된 사례·결정례 | `prec` 판례 | 판시사항 / 판결요지 / 참조조문 |

이렇게 한 이유는 세 가지다.

1. **FR-013의 metadata 요건을 이미 만족한다.** source, agency, published_at,
   doc_type이 응답에 구조화되어 있다. 스크래핑으로는 이걸 일일이 추론해야 한다.
2. **원문 링크가 있다.** 사용자가 참고자료를 직접 확인할 수 있다.
3. **출처가 공식이다.** 임의의 블로그나 요약글이 섞이지 않는다.

법령해석례가 특히 유용하다. "이 조문을 이런 상황에 어떻게 적용하는가"라는
질의–회답 구조 자체가 우리가 필요로 하는 실무 맥락이다.

## 3. 파이프라인

```
법제처 (expc / admrul / prec)
      │  LawPortalLoader
      ▼
RagDocument  ← source·agency·published_at·doc_type·related_law_names
      │  chunk_document
      ▼
RagChunk[]   ← metadata 승계, 제목을 각 청크에 부착
      │  OpenAIEmbedder (배치 64)
      ▼
Vector Store (Chroma → Pinecone)
      │  Retriever: Top-K + 법령명 필터 + 유사도 하한 + 문서 중복 제거
      ▼
RagContext[] → ContextPacket.rag → 프롬프트의 [참고자료] 블록
      │
      ▼
Validator: 범위 밖 [Rn] 인용 차단 → reference_evidence
```

### 3-1. 청킹 — 구조를 존중한다

고정 길이로 자르지 않는다. `제3조(목적)` 제목과 내용이 다른 청크로 갈라지면
검색된 조각만 봐서 무슨 조문인지 알 수 없다.

- 조문(`제N조(...)`), 항(`①`), 섹션 라벨(`[질의요지]`, `[회답]`, `[판시사항]`)에서 자른다
- 경계 조각이 너무 짧으면 앞 조각에 붙인다
- **문서 제목을 각 청크 앞에 붙인다** — 검색 결과만 봐도 출처를 알 수 있어야 한다
- 청크 id는 내용 해시라 **다시 색인해도 중복이 쌓이지 않는다**

### 3-2. 검색 — 네 겹으로 거른다

| 단계 | 목적 |
|---|---|
| 벡터 유사도 Top-K | 의미적으로 가까운 조각 |
| **법령명 필터** | 다른 법의 해석례가 섞이면 오해를 만든다 (FR-013) |
| **유사도 하한 (0.25)** | 관련 없는 참고자료는 없느니만 못하다 |
| **문서 단위 중복 제거** | 같은 문서의 여러 청크가 상위를 독점하는 것 방지 |

**질의는 조문 원문 전체가 아니다.** `법령명 + 조문제목 + 사용자 업종·직무 +
원문 앞 300자`를 쓴다. 원문을 통째로 넣으면 조문의 형식적 문구가 유사도를
지배해서, 정작 실무 맥락을 담은 해석례가 밀린다.

## 4. "참고자료 없음"은 정상이다 (BR-005)

이 설계에서 가장 중요한 부분이다. 검색 결과가 0건일 수 있고, 그것은 오류가 아니다.

빈 목록이 돌아오면:

1. Context Builder가 프롬프트에 **"검색된 참고자료가 없습니다. 참고자료를
   지어내지 마십시오."** 를 명시한다
2. Validator가 범위 밖 `[Rn]` 인용을 **REJECT** 한다 (`find_phantom_rag_refs`)
3. 화면은 "관련 참고자료를 찾지 못했습니다. 조문만으로 판단했다는 뜻이며,
   없는 출처를 지어내지 않습니다."를 보여준다

**실패도 빈 목록으로 흡수한다.** 임베딩 실패, 저장소 오류, 인덱스 부재 —
어느 것도 분석을 막지 않는다. 참고자료는 없어도 분석이 성립하기 때문이다.
여기서 억지로 무언가를 채우면 위 세 겹의 방어가 전부 무력해진다.

## 5. 저장소 — Chroma에서 Pinecone으로

`VectorStore` Protocol로 분리했다 (ADR-008).

| 구현 | 용도 |
|---|---|
| `ChromaVectorStore` | 로컬·개발. 디렉터리에 영속 |
| `InMemoryVectorStore` | 테스트. 네트워크 없이 코사인 유사도 직접 계산 |
| Pinecone | 운영 전환 시 구현 |

Chroma의 기본 임베딩 함수를 쓰지 않고 **우리가 만든 벡터를 직접 넣는다.**
그렇지 않으면 수집과 검색에서 다른 모델이 쓰일 위험이 있다.

## 6. 구현 중 겪은 것

### 6-1. 법령명 표기가 문서마다 다르다

법령명 필터가 관련 판례를 **전부** 걸러냈다. 원인은 띄어쓰기였다.

| 출처 | 표기 |
|---|---|
| 법령 API | `개인정보 보호법` |
| 판례 제목 | `개인정보보호법위반[...]` |

공백을 무시하고 비교하도록 고쳤다(`normalize_law_name`). 같은 법을 다르게 띄어
쓴다는 사실을 실제 데이터에서 확인하기 전에는 보이지 않는 문제였다.

### 6-2. 판례는 「」로 법령을 인용하지 않는다

`related_law_names`는 본문의 `「법령명」` 인용에서 뽑는다. 그런데 판례 제목은
`개인정보보호법위반`처럼 괄호 없이 쓰므로 태그가 비었고, 법령명 필터에서
전부 탈락했다. **수집 검색어를 관련 법령에 함께 기록**해 해결했다.

### 6-3. 필터를 뒤에 적용하면 후보가 말라붙는다

벡터 검색으로 상위 15건을 받아 법령명으로 걸렀더니 15건이 모두 탈락해 0건이
됐다. 필터를 통과할 후보가 남도록 과다 조회 배수를 20배(최대 200건)로 올렸다.

**교훈:** 벡터 검색 뒤에 붙는 필터는 조회량과 함께 설계해야 한다. 필터가
빡빡할수록 더 많이 받아야 한다.

### 6-4. 참고자료가 화면을 압도했다

법령해석례 본문이 길어서, 펼쳐 두니 보조 정보인 참고자료가 법적 근거보다 큰
자리를 차지했다. 기본을 접힌 상태로 두고 기관·유형·일자만 보이게 했다.

## 7. 실측 (2026-09-21)

```
검색어: 개인정보, 근로기준법
수집:   문서 22건 (법령해석례 10 · 행정규칙 6 · 판례 6)
색인:   청크 100개

근로기준법 제60조(연차 유급휴가) 검색 → 3건
  0.680  법제처 · 법령해석례 · 「근로기준법」 제60조제1항 및 제2항 등 관련
  0.643  법제처 · 법령해석례 · 제60조(업무상 부상으로 인한 휴업…) 관련
  0.614  법제처 · 법령해석례 · 제59조 제1항(연차유급휴가의 산정) 관련

하천법 제17조 검색 → 0건  (관련 없는 법령이므로 정상)
```

조문 번호 수준까지 맞는 해석례가 잡힌다. 분석 파이프라인에 연결한 뒤에도
Validator를 통과했고, 세 근거가 분리된 채로 화면에 표시된다.

## 8. 운영

```bash
# 인덱스 구축 (기본 검색어: 개인정보·근로기준법·산업안전보건법·남녀고용평등·전자상거래)
.venv/bin/python scripts/ingest_rag.py

# 검색어 지정
.venv/bin/python scripts/ingest_rag.py 개인정보 근로기준법

# 인덱스 현황
.venv/bin/python scripts/ingest_rag.py --status
```

`RAG_ENABLED=false`(기본값)이면 참고자료 없이 동작한다. 인덱스를 만들지 않은
환경에서도 분석이 정상적으로 돌아가야 하기 때문이다.

## 9. 남은 것

| 항목 | 상태 |
|---|---|
| Pinecone 전환 | 미구현. Protocol은 준비됨 |
| 보도자료 수집 | 미구현. 법제처에 해당 target이 없어 별도 소스 필요 |
| 인덱스 갱신 주기 | 수동. 스케줄러는 이번 프로젝트 제외 범위 |
| 검색 품질 평가 | 미구현. 현재는 조문별 검색 결과를 눈으로 확인한 수준 |

**검색 품질을 숫자로 측정하지 않았다.** 적용 판정은 `evaluation/`에서 Q1~Q6로
측정하지만, 참고자료가 실제로 유용한지는 아직 평가셋이 없다. 이것이 RAG 쪽의
가장 큰 공백이다.
