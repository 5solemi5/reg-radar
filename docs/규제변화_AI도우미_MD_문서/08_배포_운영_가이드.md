## 1. 배포 구성

```
브라우저
   │
   ├─ https://<app>.vercel.app          Next.js (Vercel)
   │        │
   │        ├─ 로그인 ─────────────────→ Supabase Auth
   │        └─ 데이터 ─────────────────→ FastAPI
   │                                        │
   └────────────────────────────────────────┤
                                            ├─→ Supabase Postgres
                                            ├─→ 법제처 OPEN API
                                            └─→ OpenAI
```

**프론트와 백엔드를 분리해 배포한다.** 기획서 §8의 구성이며, 백엔드를 서버리스에
올리지 않는 이유는 아래와 같다.

### 1-1. 백엔드를 Vercel에 올리지 않는 이유

`POST /analyses`는 202를 즉시 반환하고 분석을 백그라운드에서 돌린다(실측 20~40초).
**서버리스 함수는 응답을 보내는 순간 종료되므로 그 작업이 잘린다.** 실행 시간
한도(현재 Hobby 300초)는 문제가 아니고, 구조가 맞지 않는다.

Vercel에 올리려면 분석을 동기 처리로 바꿔야 하는데, 그러면 API 계약(202+폴링)과
프론트 폴링 로직을 함께 고쳐야 하고 W5 이후 붙는 오래 도는 작업마다 같은 제약에
부딪힌다. 상시 실행 호스트(Railway, Render, Fly.io, Cloud Run)를 쓴다.

### 2-1. GitHub에 올리기

현재 저장소에 원격이 없다. 커밋에 비밀정보가 없음은 확인했지만, 푸시 전에 한 번 더 본다.

```bash
# 비밀정보 최종 확인
git grep -nI --cached -E 'sk-proj-|postgresql://.*:.*@|SUPABASE_JWT'

# 원격 추가 후 푸시
git remote add origin https://github.com/<계정>/<저장소>.git
git push -u origin main
```

`.env`, `.env.e2e.local`, `.chroma/`, `.snapshots/`는 gitignore되어 있다.

## 3. 백엔드 배포 (Railway 예시)

### 3-1. 환경변수

`backend/.env.production.example`을 참고한다. **파일을 올리지 말고 플랫폼
대시보드에 입력한다.**

| 변수 | 값 | 비고 |
|---|---|---|
| `APP_ENV` | `production` | |
| `AUTH_MODE` | `supabase` | `dev`면 **기동 거부** |
| `STORAGE` | `postgres` | `memory`면 **기동 거부** |
| `DATABASE_URL` | Supabase Session pooler URI | Transaction pooler는 asyncpg와 맞지 않음 |
| `SUPABASE_URL` | `https://xxxx.supabase.co` | JWKS 공개키 조회용 |
| `CORS_ORIGINS` | `https://<app>.vercel.app` | localhost가 있으면 **기동 거부** |
| `OPENAI_API_KEY` | | |
| `LAW_API_OC` | | |
| `LLM_MODEL` | `gpt-4o` | gpt-4o-mini는 Q4 재현율 60%로 NFR-003 미달 |
| `RAG_ENABLED` | `false` 또는 `true` | §5 참조 |
| `DECREE_PAIRING_ENABLED` | 기본 `true` | 위임된 시행령 조문을 함께 조회한다 (ADR-025). 법제처 호출이 법령당 1~2건 는다. 법제처 장애 시 `false`로 끄면 위임이 보류 근거로 남는 이전 동작이 된다 — 판정이 보수적으로 바뀔 뿐 서비스는 계속 돈다 |

**설정 실수는 기동 단계에서 막힌다.** 위험한 조합을 넣으면 서버가 뜨지 않고
무엇이 문제인지 알려준다. 운영에서 조용히 잘못 뜨는 것보다 낫기 때문이다.

### 3-2. 배포

`backend/Dockerfile`이 있다. Railway는 `railway.toml`을 읽어 자동 인식한다.

```bash
# 프로젝트 루트가 아니라 backend/ 를 루트로 지정해야 한다
Root Directory: backend
```

마이그레이션은 `Procfile`의 release 단계에서 자동 적용된다. 수동으로 하려면:

```bash
python scripts/migrate.py
```

적용 여부는 `schema_migrations`에 기록되므로 두 번 실행해도 안전하다.

### 3-3. 확인

```bash
curl https://<백엔드-도메인>/api/v1/health
```

```json
{
  "status": "ok", "env": "production", "auth_mode": "supabase",
  "storage": "postgres", "database_connected": true,
  "rag_enabled": false, "rag_indexed_chunks": 0,
  "law_api_configured": true, "llm_configured": true, "llm_model": "gpt-4o"
}
```

`database_connected: false`면 `DATABASE_URL`을 확인한다. Direct connection은
IPv6라 실패할 수 있으니 **Session pooler**를 쓴다.

## 4. 프론트엔드 배포 (Vercel)

```
Root Directory: frontend
Framework: Next.js (자동 감지)
```

환경변수 세 개:

| 변수 | 값 |
|---|---|
| `NEXT_PUBLIC_API_BASE_URL` | `https://<백엔드-도메인>/api/v1` |
| `NEXT_PUBLIC_SUPABASE_URL` | `https://xxxx.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | `sb_publishable_...` |

세 값 모두 브라우저에 노출되도록 설계된 공개 값이다. 실제 권한은 RLS와 백엔드의
JWT 검증이 통제한다.

**배포 순서가 중요하다.** Vercel 도메인이 정해진 뒤에 백엔드의 `CORS_ORIGINS`를
그 도메인으로 설정해야 한다. 순서가 어긋나면 화면은 뜨는데 API 호출이 전부
막힌다(브라우저 콘솔에 CORS 오류).

`vercel.json`에 기본 보안 헤더를 넣어 두었다.

## 5. RAG 인덱스 — 배포 시 주의

Chroma는 **로컬 디렉터리**에 저장한다. 컨테이너를 다시 띄우면 인덱스가 사라진다.

문제는 이것이 조용히 일어난다는 점이다. 참고자료 0건은 BR-005에 따라 정상
상태로 처리되므로 오류가 나지 않고, 그냥 "참고자료를 찾지 못했습니다"만 나온다.

세 가지 선택지가 있다.

| 선택 | 방법 | 비고 |
|---|---|---|
| **A. 끄기** | `RAG_ENABLED=false` | 가장 단순. 참고자료 없이 동작 |
| **B. 볼륨** | 영구 볼륨 마운트 후 `CHROMA_PERSIST_DIR=/data/.chroma` | 배포 후 `scripts/ingest_rag.py` 1회 실행 |
| **C. Pinecone** | 미구현 | `VectorStore` Protocol은 준비됨 (ADR-008) |

**확인 방법:** `/api/v1/health`의 `rag_indexed_chunks`가 0이면 인덱스가 없는 것이다.
기동 로그에도 경고가 남는다.

## 6. 장애 대응

### 6-1. 증상별

| 증상 | 확인 | 원인 |
|---|---|---|
| 서버가 뜨지 않음 | 기동 로그 | 운영 설정 검증에 걸림. 로그가 무엇이 문제인지 알려준다 |
| 화면은 뜨는데 모든 API가 실패 | 브라우저 콘솔 | `CORS_ORIGINS`에 Vercel 도메인이 없음 |
| 모든 요청이 401 | `health`의 `auth_mode` | `SUPABASE_URL` 누락 또는 JWKS 조회 실패 |
| 분석이 계속 RUNNING | `ai_traces`의 실패 기록 | LLM 오류. `DELETE /analyses/{id}`로 취소 |
| 참고자료가 항상 0건 | `health`의 `rag_indexed_chunks` | 인덱스 미구축 (§5) |
| 분석이 항상 실패 | `health`의 `law_api_configured` | 법제처 OC 문제 또는 API 장애 |

### 6-2. 관측

```bash
python scripts/trace_report.py            # 최근 분석: 조문 수·토큰·소요
python scripts/trace_report.py --chains   # 체인별 토큰·지연
python scripts/trace_report.py --failures # 실패한 호출과 사유
```

체인 호출 단위로 latency·model·입출력 토큰·실패를 `ai_traces`에 남긴다.
**프롬프트 원문과 모델 응답 전문은 저장하지 않는다** — 관측성 도구가 개인정보
저장소가 되지 않게 하기 위해서다.

### 6-3. 비용

실측 기준 조문 1건당 약 3,800 토큰(C3~C5 합), 분석 1회(조문 6건)에 약 6만 토큰.
C4가 가장 많이 쓰며 추출 결과와 참고자료가 함께 들어가기 때문이다.
`MAX_ARTICLES_PER_ANALYSIS`(기본 12)로 상한을 조절한다.
