## 1. 배포 구성

```
브라우저
   │
   ├─ https://<app>.vercel.app          Next.js (Vercel)
   │        │
   │        ├─ 로그인 ─────────────────→ Supabase Auth
   │        └─ 데이터 ─────────────────→ FastAPI
   │                                        │
   └────────────────────────────────────────┤
                                            ├─→ Supabase Postgres
                                            ├─→ 법제처 OPEN API
                                            └─→ OpenAI
```

**프론트와 백엔드를 분리해 배포한다.** 기획서 §8의 구성이며, 백엔드를 서버리스에
올리지 않는 이유는 아래와 같다.

### 1-1. 백엔드를 Vercel에 올리지 않는 이유

`POST /analyses`는 202를 즉시 반환하고 분석을 백그라운드에서 돌린다(실측 20~40초).
**서버리스 함수는 응답을 보내는 순간 종료되므로 그 작업이 잘린다.** 실행 시간
한도(현재 Hobby 300초)는 문제가 아니고, 구조가 맞지 않는다.

Vercel에 올리려면 분석을 동기 처리로 바꿔야 하는데, 그러면 API 계약(202+폴링)과
프론트 폴링 로직을 함께 고쳐야 하고 W5 이후 붙는 오래 도는 작업마다 같은 제약에
부딪힌다. 상시 실행 호스트(Railway, Render, Fly.io, Cloud Run)를 쓴다.

## 1-2. 무료로 운영하는 구성

| 항목 | 선택 | 비용 |
|---|---|---|
| 프론트 | Vercel Hobby | 0원 |
| 백엔드 | **Render 무료** (`render.yaml` (저장소 루트)) | 0원 |
| DB·인증 | Supabase 무료 | 0원 |
| AI 호출 | OpenAI | **유일한 실제 지출** |

Railway는 체험 크레딧 소진 후 월 $5라 무료가 아니다. `railway.toml`은 그대로
두었으므로 유료로 전환하려면 그쪽을 쓰면 된다.

**대가는 cold start다.** Render 무료 티어는 15분간 요청이 없으면 인스턴스를
잠재우고, 다시 깨우는 데 30~60초가 걸린다. 그동안 화면이 멈춰 있으면 사용자는
고장으로 읽으므로, 프론트엔드가 3초 넘게 응답이 없으면 배너로 알린다
(`BackendWakingBanner`). 무료 티어를 쓰는 것은 선택이지만 그 대가를 사용자에게
숨기는 것은 다른 문제다.

분석이 202 응답 후 백그라운드에서 수십 초 도는 것은 문제가 되지 않는다. Render
웹 서비스는 응답을 보낸 뒤에도 프로세스가 살아 있다. 잠드는 기준은 15분 무요청이다.

### AI 호출 비용을 유한하게 묶는다

분석 1회가 약 6만 토큰이다(gpt-4o 기준 대략 $0.2~0.3). 가입이 열린 공개
배포에서 상한이 없으면 OpenAI 키를 열어 두는 것과 같다.

`uq_analyses_one_active_per_user`는 **동시 1건**만 막는다. 하루에 몇 번이든
돌리는 것은 막지 못한다. 그래서 일일 상한을 따로 둔다.

| 변수 | 기본값 | 뜻 |
|---|---|---|
| `DAILY_ANALYSIS_LIMIT_PER_USER` | 10 (배포는 5) | 사용자 1명의 하루 분석 수. 0이면 무제한 |
| `DAILY_ANALYSIS_LIMIT_TOTAL` | 200 (배포는 50) | 전체 합산. 계정을 여러 개 만드는 경우를 막는다 |

한도 소진은 `429 daily_limit_exceeded`로 응답하며, 화면에서는 오류가 아니라
안내로 보여준다 — 고장이 아니라 설계된 상한이기 때문이다.

실패한 분석도 센다. 빼면 실패를 유도해 우회할 수 있고, 실패해도 LLM 호출은
이미 나간 뒤라 비용은 발생한 상태다.

**여기에 더해 OpenAI 대시보드에서 하드 예산 상한을 걸어 둔다.** 애플리케이션
상한은 애플리케이션이 살아 있을 때만 유효하다.

## 3. 백엔드 배포 (Render 무료 / Railway 유료)

### 3-1. 환경변수

`backend/.env.production.example`을 참고한다. **파일을 올리지 말고 플랫폼
대시보드에 입력한다.**

| 변수 | 값 | 비고 |
|---|---|---|
| `APP_ENV` | `production` | |
| `AUTH_MODE` | `supabase` | `dev`면 **기동 거부** |
| `STORAGE` | `postgres` | `memory`면 **기동 거부** |
| `DATABASE_URL` | Supabase Session pooler URI | Transaction pooler는 asyncpg와 맞지 않음 |
| `SUPABASE_URL` | `https://xxxx.supabase.co` | JWKS 공개키 조회용 |
| `CORS_ORIGINS` | `https://<app>.vercel.app` | localhost가 있으면 **기동 거부** |
| `OPENAI_API_KEY` | | |
| `LAW_API_OC` | | |
| `LLM_MODEL` | `gpt-4o` | gpt-4o-mini는 Q4 재현율 60%로 NFR-003 미달 |
| `RAG_ENABLED` | `false` 또는 `true` | §5 참조 |
| `DECREE_PAIRING_ENABLED` | 기본 `true` | 위임된 시행령 조문을 함께 조회한다 (ADR-025). 법제처 호출이 법령당 1~2건 는다. 법제처 장애 시 `false`로 끄면 위임이 보류 근거로 남는 이전 동작이 된다 — 판정이 보수적으로 바뀔 뿐 서비스는 계속 돈다 |

**설정 실수는 기동 단계에서 막힌다.** 위험한 조합을 넣으면 서버가 뜨지 않고
무엇이 문제인지 알려준다. 운영에서 조용히 잘못 뜨는 것보다 낫기 때문이다.

### 3-2. 배포

같은 `backend/Dockerfile`을 두 호스트가 함께 쓴다.

| 호스트 | 설정 파일 | 비고 |
|---|---|---|
| **Render (무료)** | `render.yaml` (**저장소 루트**) | Blueprint로 읽는다. 비밀값 6개는 `sync: false`라 대시보드에서 직접 넣는다 |
| Railway (유료) | `backend/railway.toml` | Root Directory를 `backend`로 지정 |

> **Blueprint 파일은 저장소 루트에 있어야 한다.** 처음에 `backend/` 안에 두었더니
> Render가 `render.yaml not found on main branch`로 거부했다. 파일 안의
> `rootDir: backend`가 빌드 컨텍스트를 백엔드로 잡아 주므로 위치만 루트면 된다.

두 파일 모두 비밀값을 담지 않는다. 저장소가 공개라 커밋되는 파일에 들어가면
그대로 노출된다.

마이그레이션은 `railway.toml`의 `preDeployCommand`가 배포 때마다 먼저 실행한다.
적용 여부는 `schema_migrations`에 기록되므로 두 번 실행해도 안전하다.

> **`Procfile`의 `release:` 단계가 아니다.** Railway는 Dockerfile 빌더를 쓸 때
> Procfile을 읽지 않는다. 처음에 그것만 믿고 두었는데, 컨테이너를 실제로 띄워
> 보니 마이그레이션이 한 번도 돌지 않는 구성이었다. `Procfile`은 Nixpacks를
> 쓰는 호스트(Render·Heroku)용으로 남겨 두었다.

수동 실행은 이렇게 한다.

```bash
railway run python scripts/migrate.py
# 또는 로컬에서 운영 DATABASE_URL을 주고
DATABASE_URL="postgresql://..." python scripts/migrate.py
```

막힌다(브라우저 콘솔에 CORS 오류).

`vercel.json`에 기본 보안 헤더를 넣어 두었다.

## 5. RAG 인덱스 — 배포 시 주의

Chroma는 **로컬 디렉터리**에 저장한다. 컨테이너를 다시 띄우면 인덱스가 사라진다.

문제는 이것이 조용히 일어난다는 점이다. 참고자료 0건은 BR-005에 따라 정상
상태로 처리되므로 오류가 나지 않고, 그냥 "참고자료를 찾지 못했습니다"만 나온다.

세 가지 선택지가 있다.

| 선택 | 방법 | 비고 |
|---|---|---|
| **A. 끄기** | `RAG_ENABLED=false` | 가장 단순. 참고자료 없이 동작. **초기 배포 권장** |
| **B. 볼륨** | 영구 볼륨 마운트 + `CHROMA_PERSIST_DIR=/data/.chroma` | 이미지를 `--build-arg INSTALL_RAG=true`로 빌드해야 하고, 배포 후 `scripts/ingest_rag.py` 1회 실행 |
| **C. Pinecone** | 미구현 | `VectorStore` Protocol은 준비됨 (ADR-008) |

**chromadb는 기본 이미지에 없다.** onnxruntime 등을 끌고 와 이미지가 크게 불어나는데,
선택 A가 유효한 구성이기 때문이다. 선택 B를 쓰려면 빌드 인자를 켜야 한다.

**확인 방법:** `/api/v1/health`의 `rag_operational`을 본다.

| `rag_enabled` | `rag_operational` | 뜻 |
|---|---|---|
| `false` | `false` | 의도적으로 껐다 (선택 A) |
| `true` | `true`, 청크 0 | 라이브러리는 있는데 **인덱스가 비었다** → 적재 필요 |
| `true` | `false` | 아예 못 쓴다. `rag_error`에 이유가 있다 |

`rag_indexed_chunks`만 보면 이 셋이 구분되지 않는다. 실제로 배포 검증에서
`ModuleNotFoundError: No module named 'chromadb'`가 '청크 0건'으로만 보였고,
적재만 하면 되는 줄 알기 쉬웠다.

## 6. 장애 대응

### 6-1. 증상별

| 증상 | 확인 | 원인 |
|---|---|---|
| 서버가 뜨지 않음 | 기동 로그 | 운영 설정 검증에 걸림. 로그가 무엇이 문제인지 알려준다 |
| 화면은 뜨는데 모든 API가 실패 | 브라우저 콘솔 | `CORS_ORIGINS`에 Vercel 도메인이 없음 |
| 모든 요청이 401 | `health`의 `auth_mode` | `SUPABASE_URL` 누락 또는 JWKS 조회 실패 |
| 분석이 계속 RUNNING | `ai_traces`의 실패 기록 | LLM 오류. `DELETE /analyses/{id}`로 취소 |
| 참고자료가 항상 0건 | `health`의 `rag_indexed_chunks` | 인덱스 미구축 (§5) |
| 분석이 항상 실패 | `health`의 `law_api_configured` | 법제처 OC 문제 또는 API 장애 |

### 6-2. 관측

```bash
python scripts/trace_report.py            # 최근 분석: 조문 수·토큰·소요
python scripts/trace_report.py --chains   # 체인별 토큰·지연
python scripts/trace_report.py --failures # 실패한 호출과 사유
```

체인 호출 단위로 latency·model·입출력 토큰·실패를 `ai_traces`에 남긴다.
**프롬프트 원문과 모델 응답 전문은 저장하지 않는다** — 관측성 도구가 개인정보
저장소가 되지 않게 하기 위해서다.

### 6-3. 비용

실측 기준 조문 1건당 약 3,800 토큰(C3~C5 합), 분석 1회(조문 6건)에 약 6만 토큰.
C4가 가장 많이 쓰며 추출 결과와 참고자료가 함께 들어가기 때문이다.
`MAX_ARTICLES_PER_ANALYSIS`(기본 12)로 상한을 조절한다.

### 6-4. 컨테이너에서 한 번은 돌려 봐야 한다

이 가이드의 초기 버전은 문법상 맞았지만 실제로는 배포되지 않는 구성이었다.
로컬에서 `uvicorn`으로 띄우면 전부 정상이라 드러나지 않았다.

```bash
cd backend
docker build -t reg-radar-backend:test .

# 1) 운영 모드로 뜨는가 + 헬스체크
docker run -d --name rr-test -p 8099:8000 --env-file .env \
  -e APP_ENV=production -e RAG_ENABLED=false \
  -e CORS_ORIGINS="https://<프론트-도메인>" reg-radar-backend:test
curl -s http://127.0.0.1:8099/api/v1/health | python3 -m json.tool

# 2) preDeployCommand가 실제로 도는가  ← 이게 핵심
docker run --rm --env-file .env -e APP_ENV=production \
  -e CORS_ORIGINS="https://<프론트-도메인>" \
  reg-radar-backend:test python scripts/migrate.py

docker rm -f rr-test
```

2번에서 `ModuleNotFoundError: No module named 'app'`이 났다. 의존성 캐시를 위해
`pyproject.toml`만 먼저 복사해 설치하므로 그 시점에 `app/`이 없어 패키지 본체가
설치되지 않고, `uvicorn app.main:app`은 작업 디렉터리가 `/app`이라 우연히 동작하지만
`python scripts/migrate.py`는 `sys.path[0]`이 `/app/scripts`라 죽는다.
`ENV PYTHONPATH=/app`으로 고쳤다.

**이 프로젝트에서 가장 많이 반복된 교훈이 여기서도 나왔다** — 실제로 실행해 보기
전에는 모른다 (09 결과 보고서 §5).
