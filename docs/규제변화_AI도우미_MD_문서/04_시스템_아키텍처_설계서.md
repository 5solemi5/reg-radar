# 04. 시스템 아키텍처 설계서

기획서와 요구사항 정의서의 기능을 실제 시스템 구성요소로 배치하고, Next.js/React · FastAPI · LangChain · 법제처 OPEN API · RAG/Vector DB · Supabase · Observability 간 책임 경계와 요청/데이터 흐름을 정의한다.

문서 상태: 개발 착수 전 설계 기준안 작성 기준일: 2026-09-21 상위 문서: 01 기획서 / 02 Persona & Use Case / 03 요구사항 정의서

Architecture Goal

## 1. 아키텍처 목표

#### 정확성

법령 사실값은 공식 데이터 계층에서만 공급하고 AI는 의미 해석에 집중한다.

#### 추적성

사용자 요청부터 법령 snapshot, RAG 근거, AI 판단, Validator 결과까지 추적 가능해야 한다.

#### 분리 가능성

Frontend, API, AI Chain, Retrieval, DB가 명확한 계약으로 분리되어 개별 교체·테스트가 가능해야 한다.

#### E2E 완결성

로그인 → 프로필 → 분석 → 판정 → 근거 → 저장 → 히스토리가 실제 웹에서 연결되어야 한다.

> **핵심 설계 문장:** “공식 법령 데이터는 deterministic data layer가 공급하고, RAG는 실무 맥락을 보완하며, LangChain/LLM은 적용 의미와 실무 함의를 판단하고, Validator가 위험한 출력을 차단한다.”

Design Principles

## 2. 설계 원칙

| ID    | 원칙                                | 구현 의미                                                                                  |
|-------|-------------------------------------|--------------------------------------------------------------------------------------------|
| AP-01 | **Official Data First**             | 법령명·조문번호·시행일·원문·기관·공식 URL은 법제처 OPEN API 또는 저장 snapshot에서만 획득. |
| AP-02 | **LLM for Semantics**               | LLM은 적용대상 의미 추출, 직무/업종 매핑, 실무 영향 설명에 사용.                           |
| AP-03 | **Deterministic Before Generative** | 신구법 diff, 식별자 매핑, 시행령 위임 문자열 감지, **규모 기준(상시근로자 수) 충족 판정**은 코드/규칙 우선. 산술과 문자열 매칭은 LLM에 맡기지 않는다. |
| AP-04 | **Fail Safe / HOLD by Default**     | 필수 정보 부족 시 확정하지 않고 HOLD로 전환.                                               |
| AP-05 | **Evidence Separation**             | 법적 근거 / RAG 참고자료 / AI 해석을 데이터 모델과 UI에서 분리.                            |
| AP-06 | **Schema First**                    | Frontend↔FastAPI, FastAPI↔AI Core, AI Structured Output 모두 명시적 schema로 연결.         |
| AP-07 | **Snapshot & Reproducibility**      | 분석 당시 법령 근거와 결과를 보존하여 과거 결과를 재현 가능하게 함.                        |
| AP-08 | **Observable AI**                   | model, prompt/chain, token, latency, error, validation 결과를 trace 단위로 관측.           |

Request & Sequence Flows

## 5. 주요 요청 흐름

### 5-1. 로그인/프로필 설정

01User → Next.js회원가입 또는 로그인. 02Next.js → AuthSupabase Auth 세션 생성. 03Next.js → FastAPI현재 사용자 profile 조회. 04FastAPI → DBprofiles에서 user_id 기준 조회. 05User직무·업종·회사 규모·관심영역 입력/수정. 06FastAPI → DB검증된 profile 저장 후 응답.

### 5-2. 규제 분석 실행 — 핵심 E2E

01User → Next.js“최근 규제 분석” 실행. 02Next.js → FastAPIPOST /analyses. 사용자 token + 분석기간 전달. 03FastAPI → DBanalysis 레코드 생성(status=running) 및 user profile 확보. 04Legal Adapter법제처 API에서 대상 법령 목록을 조회하고, **신구법 비교로 이번 개정에서 실제 변경된 조문만** 후보로 확보한다. 본문 snapshot도 함께 가져와 정규화. 05Diff Engine법제처가 표시한 변경 구간을 그대로 ChangeContext로 만든다. 신구법 응답이 없을 때만 텍스트 비교로 추정. 06Retriever법령명/업종/문서유형 metadata 기반 정부 가이드·FAQ Top-K 검색. 07Context BuilderUser Profile + Official Law + Diff + RAG docs를 하나의 입력 packet으로 구성. 08LangChain AI적용대상 추출 → 관련성 판단 → 실무 영향 → action grade를 Structured Output으로 생성. 09Validatorschema, 인용, forbidden facts, HOLD rule을 검증. 실패 시 결과 차단. 10FastAPI → DBsnapshot, analysis_result, evidence reference, trace id 저장. analysis completed 처리. 11Next.jsDashboard에서 ACTION/DECISION/AWARENESS/HOLD 우선순위로 표시.

### 5-3. HOLD 재판정

01Detail UI보류 사유(missing_context)와 함께 **해소 폼을 바로 표시**한다. 설정 화면으로 보내지 않는다. 02User상시근로자 수 또는 자유 서술로 부족한 정보를 입력. 03FastAPI`POST /results/{id}/reassess`. 프로필에 추가정보를 얹되 **프로필 자체는 바꾸지 않는다**(과거 분석은 당시 기준 보존). 04Legal근거는 **law_snapshots**에서 가져온다. 변경 내용도 최초 분석의 것을 재사용한다 — 신구법을 다시 부르면 그 사이 또 개정됐을 때 다른 근거로 판단하게 된다. 05AI + Validator해당 조문 하나만 재실행하고 검증. 06DB이전 결과를 남기고 새 결과 + hold_revisions 이력 저장.

### 5-4. Evidence 조회

01User규제 상세에서 Evidence 탭 열기. 02FastAPI → DB분석 당시 law_snapshot과 연결된 공식 근거 조회. 03FastAPIRAG evidence metadata/검색결과 조회. 04Next.js\[법적 근거\] / \[참고자료\] / \[AI 해석\] 섹션으로 분리 렌더링.

## 6. AI / RAG / 공식 데이터 경계

#### Official Legal Data

- 법령명
- 조문번호
- 시행일
- 법령 원문
- 공식 기관/URL

- 정부 가이드
- FAQ
- 행정해석
- 보도자료

**원칙:** 실무 맥락 보강용. 법적 원문과 권위를 섞지 않음.

- 적용대상 의미 추출
- 직무/업종 관련성
- 실무 영향 설명
- action grade
- HOLD 사유 구조화

**원칙:** 입력 근거 범위 안에서 해석.

## 9. 인증·보안·신뢰 경계

| 영역             | 요구사항                                                         | 아키텍처 대응                                                               |
|------------------|------------------------------------------------------------------|-----------------------------------------------------------------------------|
| 인증             | 보호 API는 인증 사용자만 접근                                    | Supabase session/token을 FastAPI에서 검증하고 user context 구성. **`AUTH_MODE=supabase`에서 Supabase JWT를 검증한다. Supabase는 프로젝트마다 ES256 비대칭 키로 서명하므로 JWKS에서 공개키를 받아 검증하고(레거시 HS256도 지원), 서명·만료·audience·sub를 모두 확인한다. `AUTH_MODE=dev`는 `X-User-Id` 헤더를 신뢰하는 로컬 전용 모드이며, `APP_ENV=production`과 함께 쓰면 앱 기동을 거부한다.** |
| 데이터 격리      | 다른 사용자의 profile/analysis/history 접근 금지                 | 모든 user-scoped query에 user_id를 **필수 인자로** 강제(저장소 Protocol). Supabase RLS 정책으로 anon key 직접 접근 경로도 차단(`migrations/002`). 남의 리소스는 403이 아니라 404. |
| Secret           | LLM/법제처/Tavily/Pinecone key를 클라이언트에 노출 금지          | server-side env로만 관리.                                                   |
| Prompt Injection | RAG 문서 또는 사용자 입력이 시스템 규칙을 무력화하지 않도록 방어 | Context 경계, system instruction, structured output, validator로 방어.      |
| 민감정보         | 관측성 도구에 불필요한 사용자 원문/secret 저장 금지              | trace payload 최소화 또는 마스킹.                                           |
| 법률 오인        | AI 결과를 법률 자문으로 단정하지 않음                            | 제품 고지 + 공식 근거/AI 해석 분리 + HOLD 전략.                             |

| **법제처 API**        | 제한된 재시도 → 검증된 snapshot/cache 사용 가능 여부 판단 | LLM이 법령 사실 대체 생성      | failed 또는 cached 기준일 표시 |
| **RAG/Vector DB**     | 검색 실패를 빈 참고자료로 처리 가능                       | 존재하지 않는 출처 생성        | “참고자료 없음/조회 실패”      |
| **LLM**               | 제한된 재시도 또는 분석 실패                              | 불완전 응답을 정상 결과로 저장 | failed + 재시도                |
| **Structured Output** | parse/schema 검증 실패 처리                               | 임의 필드 보정 후 성공 처리    | 해당 항목 실패                 |
| **Validator**         | 결과 reject                                               | 검증 실패 결과 노출            | 검증 실패                      |
| **DB**                | transaction rollback 및 error trace                       | 저장 실패를 완료로 응답        | 저장/분석 실패                 |
| **Auth**              | 401/403                                                   | 익명으로 사용자 데이터 반환    | 재로그인/권한 오류             |

## 11. 관측성 / Trace 설계

| 관측 항목  | 최소 기록 값                                                         | 목적                         |
|------------|----------------------------------------------------------------------|------------------------------|
| Request    | trace_id, analysis_id, route, status                                 | API 요청 추적                |
| Legal Data | source, law_id, snapshot id, latency, error                          | 공식 근거 수집 문제 진단     |
| RAG        | query/filter, top_k, returned count, doc ids                         | 검색 품질/0건 원인 분석      |
| LLM        | provider/model, latency, **input/output token**, ok, error            | 비용·성능·안정성 분석. `ai_traces`에 영속 |
| Validator  | validation type, pass/fail, reject reason                            | hallucination/guardrail 분석 |
| Evaluation | case id, predicted label, ground truth, FP/FN                        | 회귀 테스트 및 모델 비교     |

> **Trace 연결 규칙:** \`trace_id\`는 FastAPI 분석 요청 시 생성하고 analysis, AI trace, error log를 연결할 수 있도록 유지한다.

### 11-1. 구현 상태 (W6)

`ai_traces` 테이블에 체인 호출 단위로 기록한다. 로그만으로는 "이 분석이 토큰을
얼마나 썼는가", "어떤 체인이 느린가"를 집계할 수 없기 때문이다.

| 기록 항목 | 비고 |
|---|---|
| trace_id / analysis_id / user_id | 요청–분석–사용자 연결 |
| law_id / article_no | 어떤 조문이었는지 (**원문은 저장하지 않는다**) |
| chain / model | C3~C5 중 어느 단계, 어느 모델 |
| latency_ms / ok / error | 성능과 실패. **실패한 호출의 기록이 더 중요하다** |
| input_tokens / output_tokens | 비용 추적, 프롬프트 비대화 감지 |

**프롬프트 원문과 모델 응답 전문은 저장하지 않는다.** 사용자 프로필과 법령
원문이 그대로 남으면 관측성 도구가 개인정보 저장소가 된다 (§9). 예외 메시지에
프롬프트가 섞여 들어올 수 있어 길이도 제한한다.

**관측 기록 실패는 분석 실패로 번지지 않는다.** 관측은 부수 효과이므로, trace
저장이 실패해도 경고만 남기고 분석은 계속한다.

실측 (근로기준법 1건 · 조문 6건, 2026-09-21):

```
체인 호출 16회 · 총 토큰 60,719
  C3_target_extraction      6회 · 16,793 토큰 · 평균 4,017ms
  C4_applicability_mapping  6회 · 27,234 토큰 · 평균 2,295ms
  C5_practical_impact       4회 · 16,692 토큰 · 평균 3,009ms
```

C4가 토큰을 가장 많이 쓴다. 추출 결과와 참고자료가 프롬프트에 함께 들어가기
때문이며, 비용을 줄인다면 여기가 첫 대상이다.

### 12-0. 구현 중 추가된 결정 (ADR-009~014)

아래는 기획·설계 시점에는 없었고 **실제 구현·실측 과정에서 드러나 내린 결정**이다.

| ADR | 결정 | 이유 | Trade-off |
|---------|------|------|-----------|
| ADR-009 | **분석 대상은 법제처 신구법 비교가 알려준 변경 조문으로 한정** | “최근 규제 변화를 분석한다”의 대상이 미정의 상태였다. 근로기준법 한 건이 132개 조문이라 전량 LLM 투입은 불가능하고, 조문별 시행일자는 개정 여부와 무관하게 전부 법령 시행일자로 채워져 후보 선정 신호로 쓸 수 없었다. 신구법 비교 API는 변경 조문만 반환하고 변경 구간을 `<P>`로 직접 표시한다. | 신구법 응답이 없는 법령(제정 직후 등)은 건너뛴다. 직전 개정 1회분만 다룬다. |
| ADR-010 | **규모 기준 충족 판정을 코드로 이관** | 초기에는 “상시 10명 이상” 같은 수치 기준 판정을 LLM에 맡겼다. 실측에서 80명 프로필에 대해 “상시 10명 이상의 정의가 필요하다”며 보류를 내는 현상이 나왔다. 산술은 의미 해석이 아니므로 AP-03을 적용했다. | 조문 표현이 정규식 범위를 벗어나면 기준을 놓친다. 놓치면 보류 사유가 생성되지 않으므로 케이스 확대 시 재점검이 필요하다. **실제로 일어났다** — 중대재해처벌법 제3조의 “상시 근로자**가** 5명 미만”이 조사 때문에 매칭되지 않았다(ADR-029). 예고한 재점검을 `holdout_v2` 후보 조문을 읽다가 하게 됐다. |
| ADR-011 | **판정 절차를 ‘대상 집단 확인 → 세부 기준 확인’ 2단계로 고정** | IT 서비스 회사가 ‘유해화학물질 영업자’인지는 물어볼 것도 없이 무관인데, 조문에 위임 문구가 있다는 이유만으로 보류가 나왔다. 대상 집단 여부를 먼저 묻지 않아 생긴 문제다. | 프롬프트가 길어진다. 대상 집단 판단 자체가 애매한 조문에서는 여전히 어렵다. |
| ADR-012 | **근거 없는 APPLICABLE은 Validator가 REJECT** | 검증된 원문 인용이 하나도 남지 않은 ‘해당’ 확정은 이 서비스에서 가장 위험한 출력(Q2 오탐)이다. 인용을 제거만 하고 결과를 통과시키면 근거 없는 확정이 사용자에게 노출된다. | 모델이 인용에 실패하면 유효한 판정도 버려진다. HOLD·NOT_APPLICABLE에는 적용하지 않아 균형을 맞췄다. |
| ADR-013 | **기본 LLM을 gpt-4o로 고정** | gpt-4o-mini는 15케이스 평가에서 Q4 재현율 60%로 NFR-003(≥90%)을 충족하지 못했다. 관련 규제를 놓치는 것은 보류보다 나쁜 실패다. | 비용 증가. 케이스 확대 후 재검토 대상이다. |
| ADR-014 | **저장소를 Protocol로 분리하고 W2는 인메모리 구현 사용** | 프론트엔드를 Supabase보다 먼저 붙이기 위해(01 기획서 §12-0). 사용자 데이터 조회는 전부 `user_id`를 필수 인자로 받아 데이터 격리를 시그니처 수준에서 강제한다. | 프로세스 재시작 시 데이터가 사라진다. W4까지의 한시적 상태다. |

| ADR-015 | **분석 후보를 프로필 기반으로 선정** | 시행일 내림차순 최신 N건을 집었더니 IT 서비스 HR 담당자에게 ‘감사원사무처 직제’, ‘하천법 시행규칙’이 분석 대상으로 나왔다. 판정은 정확히 ‘무관’이었으나 볼 필요 없는 것에 LLM 비용을 썼다. `interests`는 기획서 §9에서 개인화 기준으로 정의됐으나 그동안 쓰이지 않았다. | 관심 영역 밖의 중요한 개정을 놓칠 수 있다. 검색어 매핑을 수동으로 관리해야 한다. |
| ADR-016 | **조문 분석을 제한된 동시성으로 실행하고 총량에 상한** | 조문 1건이 LLM 3회(C3~C5)를 쓴다. 순차 실행에서 개정 범위가 넓은 법령이 걸리자 분석이 3분을 넘겨 NFR-006을 위반했다. 동시성 4 + 분석당 조문 12건 상한으로 42초까지 줄였다. | 조문 수가 많으면 일부는 분석되지 않는다. 법령 간 번갈아 뽑아 한 법령이 상한을 독식하지 않게 했다. |

| ADR-017 | **저장소를 asyncpg 직접 연결로 구현 (PostgREST 미사용)** | Supabase는 관리형 Postgres다. 저장소가 이미 Protocol로 분리되어 있어 SQL을 직접 쓰는 편이 쿼리 의도를 드러내기 좋고, 무엇보다 **로컬 Postgres에서 그대로 테스트할 수 있다.** 실제로 같은 테스트를 인메모리·Postgres 양쪽에 돌려 두 건의 버그를 잡았다. | Supabase 클라이언트 기능(실시간 구독 등)을 쓰려면 별도 연동이 필요하다. |
| ADR-018 | **도메인 규칙을 DB 제약으로 이중화** | 애플리케이션이 이미 규칙을 강제하지만, 동시 요청이 겹치면 코드만으로는 막을 수 없다. 특히 '사용자당 진행 중인 분석 1개'(FR-003)는 부분 유니크 인덱스가 필요하다. 보류-missing_context, 행동등급-판정축 제약도 함께 걸었다. | 스키마 변경 비용이 늘고, 인메모리 구현과 방어 깊이가 달라진다(테스트에 명시). |

| ADR-019 | **JWT를 JWKS 공개키로 검증 (HS256 공유 시크릿이 아니라)** | Supabase 프로젝트를 실제로 연결해 보니 현재 서명 키가 ES256 비대칭 키였고 HS256 공유 시크릿은 '이전 키'로 밀려나 있었다. HS256 전제로 짠 검증은 지금 발급되는 토큰을 거부한다. 공개키 방식은 서버가 비밀키를 보관하지 않아 더 안전하기도 하다 — 검증자가 토큰을 위조할 수 없다. | JWKS 조회에 네트워크가 필요하다. 캐시하되 만료를 두고, 공개키를 못 받으면 통과시키지 않고 실패시킨다. |
| ADR-020 | **브라우저는 DB에 직접 접근하지 않는다 (Data API 비활성)** | Supabase의 Data API(PostgREST)를 켜면 테이블 위에 공개 REST 엔드포인트가 열린다. 우리 백엔드는 asyncpg로 직접 붙으므로 그 경로가 필요 없고, 쓰지 않는 문은 잠그는 편이 낫다. 프론트는 로그인(세션/토큰 발급)에만 Supabase를 쓴다. | 나중에 supabase-js로 테이블을 직접 조회하려면 다시 켜야 한다. |

| ADR-021 | **RAG 소스를 법제처의 다른 target으로 한정 (스크래핑하지 않음)** | 기획서는 정부 가이드·FAQ·행정해석을 RAG 대상으로 정했다. 법제처 OPEN API가 법령해석례(`expc`)·행정규칙(`admrul`)·판례(`prec`)를 제공하며, FR-013이 요구하는 source·agency·published_at·doc_type이 이미 구조화되어 있고 원문 링크도 있다. 스크래핑으로는 이를 매번 추론해야 하고 출처 신뢰성도 떨어진다. | 보도자료는 해당 target이 없어 미구현으로 남는다. |
| ADR-022 | **검색 결과 0건을 실패가 아닌 정상 상태로 설계** | 임베딩 실패·저장소 오류·인덱스 부재를 모두 빈 목록으로 흡수한다. 참고자료는 없어도 분석이 성립하므로(BR-005) 여기서 분석을 막거나 억지로 무언가를 채우면, 프롬프트 경고·Validator의 phantom 인용 차단·화면 안내라는 세 겹의 방어가 무력해진다. | 인덱스가 비어 있어도 조용히 동작하므로, 인덱스 상태는 `ingest_rag.py --status`로 따로 확인해야 한다. |

| ADR-023 | **재판정에 저장된 snapshot을 쓴다 (법제처 재조회 아님)** | 재판정 시점에 신구법을 다시 부르면 그 사이 또 개정됐을 때 최초 판정과 다른 근거로 판단하게 된다. 사용자는 "같은 조문인데 왜 결과가 다르냐"를 이해할 수 없다. `law_snapshots`를 보존해 둔 이유가 이것이다 (AP-07, BR-006). | snapshot이 없으면 재판정이 불가능하다. 없는 근거로 판단하느니 실패를 드러낸다 (BR-001). |
| ADR-024 | **재판정 입력을 프로필에 자동 반영하지 않는다** | 사용자가 '이 조문에 한해' 정보를 주는 경우가 있고, 과거 분석은 당시 프로필 기준으로 보존되어야 한다 (FR-002 AC). 프로필 반영은 `apply_to_profile`로 명시적으로 선택하며, **재판정이 성공한 뒤에** 적용한다 — 실패했는데 프로필만 바뀌면 무엇이 적용됐는지 알 수 없다. | 같은 정보를 매번 입력해야 할 수 있다. 체크박스로 한 번에 처리한다. |

| ADR-025 | **위임된 하위법령 조문을 함께 조회해 판정 근거로 준다** | 홀드아웃 실측에서 오답 6건이 **전부** 이 문제였다. 조문에 "대통령령으로 정한다"가 있으면 그 위임이 적용을 가르는지 세부 절차에 관한 것인지와 무관하게 보류가 나왔다. 최저임금법 제6조의 위임은 *산입 임금의 범위*에 관한 것인데도 "최저임금을 줘야 하는지 모르겠다"고 답한다. 위임 문구만 보이고 위임된 **내용**이 안 보이니 모델로서는 달리 할 수 있는 게 없었다. 시행령 조문이 "법 제6조제4항에 따라"로 모법을 직접 참조하므로 역매핑이 가능하다 — 추론이 아니라 원문에 적힌 사실이다. | 법제처 호출이 법령당 1~2건 는다. `decree_pairing_enabled`로 끌 수 있다. 하위법령을 못 찾으면 기존대로 위임이 보류 근거로 남는다. |
| ADR-026 | **역참조는 각 항의 '근거 절'에서만 인정한다** | 이행 조문은 첫머리에서 근거를 밝히지만("① 법 제17조제1항에 따라 …"), 호·목 안쪽의 "법 제31조에 따른 개인정보 보호책임자"는 다른 규정을 설명하려고 조문을 명사처럼 쓴 것이다. 구분하지 않았더니 개인정보 보호법 제31조에 무관한 시행령 조문 셋이 근거로 붙었다. **틀린 근거는 근거가 없는 것보다 나쁘다.** | 근거를 조문 끝에서 밝히는 예외적 형식은 놓친다. 조문제목 일치가 2차 신호로 이를 일부 보완한다. |
| ADR-027 | **하위법령이 기준을 또 넘기면 보류를 유지한다** | 산업안전보건법 시행령 제16조는 "별표 3과 같다"로 끝나는데 별표는 법제처 조문 본문에 딸려 오지 않는다. 조문을 붙였다는 이유로 보류를 풀었더니 모델이 별표 번호만 보고 150인 제조업을 **무관**으로 판정했다. 관련 규제를 놓치는 것은 보류보다 나쁜 실패다(NFR-003). 판단 기준은 '조문을 찾았는가'가 아니라 '기준을 손에 넣었는가'이며, 목록 맨 앞의 가장 구체적인 이행 조문으로 결정한다. | 별표에 실린 기준은 당분간 보류로 남는다. 별표 조회는 후속 과제다. |

| ADR-028 | **규모 기준이 '적용 조건'인지 '배제 단서'인지 표시한다** | 같은 "상시 30명"이라도 방향이 정반대일 수 있다. 근로자참여법 제4조는 "상시 30명 미만은 그러하지 아니하다"로 설치 의무를 **배제**한다. 그런데 블록이 '충족/미충족'으로만 알려주니 80명 회사에게 "상시 30명 미만 → 미충족"이 갔다. 모델이 이를 '적용 안 됨'으로 읽으면 정확히 거꾸로이고, 블록은 "이 값을 의심하지 말라"고 못까지 박아 되돌릴 길도 없었다. 코드는 산술("80명이 이 표현에 해당하는가")만 말하고, 그 기준이 배제 단서라는 **문자열 사실**을 함께 준다. 적용 여부 해석은 조문 문맥을 읽는 LLM의 몫이다. | 배제 표현이 정규식 밖의 형태면 표시가 누락된다. 그 경우 이전과 같은 상태이지 더 나빠지지는 않는다. |
| ADR-029 | **한국어 활용형 패턴을 한 모듈에 모은다** (`app/diff/korean.py`) | 같은 함정에 세 번 빠졌다 — diff 엔진에서 `정하`가 "정**한다**"를 놓쳤고, 시행령 페어링에서 같은 실수를 재현했고, 규모 판정에서 `아니하`가 "적용하지 **아니한다**"를 놓쳐 배제 조항이 적용 조건으로 분류됐다. 법조문 종결형은 `~한다`인데 사전형 어간은 `~하`로 끝나므로, 어간을 그대로 쓰면 **가장 흔한 형태만 정확히 빠진다.** 각 모듈이 따로 만들면 네 번째가 나온다. | 활용형이 늘면 오탐이 늘 수 있다. 세 번의 실패가 전부 누락(FN)이었으므로 포괄을 택했다. |

| ADR-030 | **위임 해소 여부를 '위임을 이행하는 문장' 안에서만 판단한다** | ADR-027을 조문 전체에 적용했더니 기능이 사실상 꺼졌다. 시행령 조문은 길고 호·목 안에 무관한 별표·고시 참조가 흔해서, 기준을 제대로 담은 조문까지 '미해소'로 잡혔다 — holdout_v2 1차에서 위임 케이스의 41%가 이 때문에 보류였다. 산안법 시행령 제16조는 근거 문장 자체가 "…상시근로자 수는 **별표 3과 같다**"이므로 미해소가 맞지만, 중대재해법 시행령 제4조는 "…구체적인 사항은 다음 각 호와 같다"로 기준을 담고 한참 뒤 호에서만 별표를 언급한다. 문장 단위로 가르면 둘이 구분된다. 순위도 조문제목 유사도를 1순위로 올렸다 — 참조 수가 같으면 조문번호 순으로 밀려 장애인고용법 제28조에 '공사 실적액 산정' 조문이 1순위로 붙었고, 엉뚱한 조문이 보류 해제를 결정하고 있었다. | 근거 문장을 특정하지 못하면 조문 전체를 본다(보수적). 이 폴백을 첫 문장만 보게 했다가 `holdout_v1`이 회귀했다 — 파견법 시행령이 모법을 `「…법률」(이하 "법"이라 한다) 제5조`로 불러 역참조가 안 잡혔고, 별표로 넘기는 ①항을 건너뛰었다. 자기정의 형태를 인식하게 하고 폴백을 넓혔다. |

| ADR-031 | **대상 집단 판단에 필요한 정보가 없으면 '무관'도 확정하지 않는다** | 규모 미상은 코드가 보류를 강제하는데, '이 회사가 도급인인가' 같은 지위 미지수는 LLM에 맡겨져 있었다. 프롬프트가 "보류를 남용하지 마십시오"로 강하게 눌러 놓아 모르는 것도 업종만 보고 결정했다 — holdout_v2에서 보류 재현율 40%로 나타났고 놓친 3건이 전부 이 유형이었다. 모델에게 묻는 질문을 '적용되는가'에서 **'판단할 근거가 프로필에 있는가'**(`target_group_basis`)로 바꾸고, 근거가 없으면 코드가 보류로 내린다. 위임·규모 사유와 달리 이 사유는 **무관도 강등**한다 — 대상인지 모르는데 '무관'이라고 말하는 것은 근거 없는 확정이고, 놓치는 쪽이 보류보다 나쁘기 때문이다 (NFR-003). | 판단 자체는 여전히 LLM이 한다. 코드는 그 결과를 강제할 뿐이다. |
| ADR-032 | **프로필 판단의 근거도 인용 검증한다** | ADR-031만으로는 부족했다. holdout_v3 1차에서 오답 6건이 전부 무관 확정이었는데, 모델이 "업종이 IT 서비스로 정보통신서비스 제공자에 해당하지 않는다", "IT 서비스 업종의 **HR 담당자**는 '사업자등'에 해당하지 않는다"처럼 근거 없이 단정했다. 조문 인용을 원문 substring으로 검증하듯(FR-021) 프로필 판단도 근거를 요구하고 대조한다 — 모델은 `profile_evidence`에 프로필 한 줄을 그대로 복사해야 하고, 실제 프로필에 없으면 판단이 버려져 보류로 내려간다. **요구만 하고 대조하지 않으면 모델은 그럴듯한 문장을 지어낸다.** 판정 주체가 회사이지 담당자 개인이 아니라는 것도 프롬프트에 못 박았다. | 인용 검증은 '그 줄이 있는가'만 본다. '그 줄이 그 결론을 뒷받침하는가'는 못 본다 — holdout_v3에 남은 오답 3건이 그 종류다. 근거 조작은 막았지만 근거 해석은 여전히 LLM의 몫이다. 근거 누락은 스키마 예외로 막지 않는다. 거기서 던지면 구조화 출력 파싱이 실패해 분석 전체가 죽는다. 실패해야 한다면 보류 쪽으로 실패한다. |

> **판정 축의 긴장 관계 (운영 시 주의):** Q2(오탐률)와 ‘과도한 보류율’은 서로를
> 잡아먹는다. 한쪽만 보고 프롬프트를 조정하면 판정 임계값만 이동하고 실제 능력은
> 그대로다. 실측에서 보류를 0%로 만든 수정이 Q4 재현율을 80%→60%로 떨어뜨린 적이
> 있다. **두 지표는 반드시 함께 본다.**
