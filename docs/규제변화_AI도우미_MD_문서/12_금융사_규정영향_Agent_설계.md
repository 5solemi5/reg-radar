## 3. R1 설계 — 평가를 믿을 수 있게

### 3-1. LLM 응답 녹화·재생 (cassette)

- 모든 LLM 호출은 `ChainRunner.invoke` 한 곳을 지난다. 여기에 `Cassette`를 꽂는다.
- 키 = sha256(체인 이름, 모델, 시스템 프롬프트, 사용자 프롬프트, 출력 스키마 JSON 스키마).
  **프롬프트나 스키마가 한 글자라도 바뀌면 키가 바뀐다.**
- 모드
  - `off`: 지금과 같다(운영 기본값).
  - `record`: 실제 호출 후 파싱된 출력과 토큰 수를 JSONL에 추가한다.
  - `replay`: LLM을 부르지 않고 저장된 출력을 돌려준다. 키가 없으면 **실패한다**(조용히 실제 호출로 넘어가지 않는다).
- 저장 위치: `evaluation/cassettes/<데이터셋>__<모델>.jsonl`. 프롬프트·응답 원문 미저장 정책(관측성)과의 관계:
  cassette는 **평가 데이터셋 전용**이며 사용자 데이터가 들어가지 않는다. 운영 경로에서는 `off`만 허용한다(설정 가드).

### 3-2. 결과 메타데이터

`--save` 결과 JSON에 추가: `dataset_id`, `dataset_sha256`, `git_commit`, `git_dirty`, `prompt_version`(prompts.py 원문 해시),
`cassette`(모드·파일·적중 수), `tokens`(입력·출력 합), `cost_usd_estimate`(모델별 단가표, 가정값 — 단가는 설정에 두고 결과에 함께 기록).

### 3-3. Q1 노출 인용 정확도를 실제로 잰다

지금은 "Validator를 통과한 것만 노출되니 1.0"이라고 **가정**하고 1.0을 적는다. 그러면 Validator에 구멍이 생겨도 지표가 알려 주지 못한다.
바꾼다: 평가 러너가 노출되는 인용(`legal_evidence`·`delegated_evidence`)을 **Validator와 다른 독립 구현**으로 원문과 다시 대조해 비율을 잰다.
1.0이 아니면 Validator 버그다 — 그래서 이 값은 회귀 검사의 불변식이 된다.

### 3-4. 재생 기반 회귀 CI

- `scripts/check_eval_regression.py`: 지정한 데이터셋을 `--offline --replay`로 돌려 저장된 기준 지표(`evaluation/baselines/*.json`)와 **정확히** 비교한다.
- 실패 조건: 지표가 다름(코드 변경이 판정을 바꿨다), cassette 미스(프롬프트·스키마가 바뀌었다 → 녹화를 새로 하고 기준을 갱신해야 한다).
- GitHub Actions: pytest + 회귀 검사. 키도 법제처도 필요 없다(snapshot 캐시 + cassette).

### 3-5. 완료 기준

- cassette 단위 테스트: 녹화 → 재생 결과 동일, 프롬프트 1글자 변경 → 재생 실패, 운영 설정에서 record/replay 금지
- 같은 cassette로 두 번 재생한 지표가 바이트 단위로 같다
- Q1 노출 정확도: 일부러 검증되지 않은 인용을 노출 근거에 끼워 넣은 테스트에서 1.0 미만이 된다
- 기존 465개 테스트 유지

## 4. R3 설계 개요 — 사내 규정 영향 분석 (R1 이후 상세화)

- **가상 금융사 사내 규정집**: "가상카드(주)" 내부통제기준·개인정보 처리 지침·금융소비자보호 내부기준 등. 모두 가상이며 그렇게 표시한다.
- **사실은 코드가**: 사내 규정 ID·조문번호는 코드가 공급하고, LLM은 후보 번호(`[P1]`…)와 `cited_spans`로만 가리킨다.
  기존 `FORBIDDEN_FACT_FIELDS` 원칙과 `find_fabricated_article_refs`를 사내 규정에도 똑같이 적용한다(허용 범위에 사내 규정 원문 추가).
- **흐름**: VALIDATED·APPLICABLE 판정 → 사내 규정 후보 검색 → C7 영향 매핑(근거 인용 검증) → C8 개정 초안(근거 인용 검증) →
  상태 `DRAFTED → IN_REVIEW → APPROVED | REJECTED` → 감사 이벤트(누가, 무엇을, 언제, 이전·이후 해시) 추가 전용.
- **역할**: 준법감시인(승인), 현업 담당(열람·의견). 백엔드는 service_role로 RLS를 우회하므로 역할은 앱 계층에서 강제한다.
- 기존 `hold_revisions`의 "덮어쓰지 않고 이력을 잇는" 패턴을 승인 이력으로 일반화한다.

## 5. 하지 않는 것

- 실제 금융사 규정·고객 데이터 사용 (전부 가상)
- 사람 승인 없이 규정을 바꾸는 자동화
- 결정적 게이트(Validator, 보류 규칙, 규모 판정)를 LLM 판단으로 대체

## 6. 구현 결과 (2026-10-11)

### 6-1. R1 — 평가 재현성 (완료)

- `app/ai/cassette.py`: 키 = sha256(체인·모델·시스템 프롬프트·사용자 프롬프트·출력 스키마). 녹화(record)·재생(replay)·끔(off).
- 4개 데이터셋 gpt-4o 녹화. 녹화 비용(단가 가정 $2.5/$10 per 1M): 약 **$2.68** (applicability_v1 0.72 · holdout_v1 0.60 · v2 0.80 · v3 0.57).
- 재생 결과(키·네트워크 없이): 판정 정확도 100 / 93.8 / 90.9 / 88.9%, cassette 미스 0. **이 4개 셋은 이미 튜닝에 쓰였다 — 일반화 성능이 아니라 회귀 기준이다.**
- Q1 노출 인용 정확도: 하드코딩 1.0을 지우고, 화면에 보이는 인용을 Validator와 다른 방식(공백 전부 제거 후 포함 여부)으로 다시 찾아 잰다. 4개 셋 모두 실측 100%.
- `evaluation/baselines/*.json` + `.github/workflows/backend-ci.yml`: 재생 지표가 기준과 한 글자라도 다르면 실패.

**녹화 중 찾은 결함 (재현성 버그)**: 같은 조문을 다른 프로필로 보는 케이스들이 C3(같은 프롬프트)를 동시에 불렀다.
LLM은 같은 입력에도 다른 답을 줄 수 있어 두 C3 답이 각자의 C4 프롬프트로 이어졌는데, 녹화에는 키당 하나만 남아 재생 때 C4가 미스났다
(holdout_v3에서 9건). 고친 것: 녹화 중 같은 키는 한 번만 실제로 부르고 동시 호출은 그 결과를 기다린다(in-flight dedupe),
이미 녹화된 키는 재사용(이어 녹화 = 빠진 호출만 과금), 실패한 호출도 녹화해 재생에서 같은 실패를 재현. 테스트 3개 추가.

### 6-2. R2 — 알려진 결함 (완료)

- **재판정 위임 조문 누락 (수정)**: `ReassessService`가 packet을 만들 때 `delegated=`를 넘기지 않았다. 최초 분석은 시행령 기준을 읽고 판정했는데
  재판정은 "대통령령에 위임되어 알 수 없다"로 돌아갈 수 있었다 — 정보를 더 줬는데 근거는 줄어드는 구조. 최초 분석과 같은 방식으로 붙이도록 고치고 회귀 테스트 2개.
- **REJECT 재생성 (구현)**: Validator가 REJECT하면 거부 사유(+ 원문에서 못 찾은 인용 문장)를 C4·C5 프롬프트에 되먹여 다시 만든다.
  상한 `REJECT_RETRY_MAX=2`. 결정적 게이트는 그대로 — 재생성한 답도 같은 검증을 통과해야 한다. 거부 사유가 없으면 프롬프트가 한 글자도
  바뀌지 않아 기존 녹화와 그대로 맞는다. 결과의 `validation.retries`·`rejected_failures`에 몇 번, 왜 다시 만들었는지 남는다.
  실측: holdout_v1의 H09(최저임금법 제11조)가 유일한 인용이 원문 대조에 실패해 REJECT였는데, 재생성 1회 뒤 VALIDATED. Q3 행동 전환 77.8→88.9%
  (이 셋은 튜닝에 쓰인 셋이라 회귀 기준이다). 추가 녹화 2건.
- **`hold_confidence_threshold` 삭제**: 정의만 있고 어디서도 읽지 않았다. 설정 파일에 있으면 동작한다고 믿게 된다. 보류 강등은 confidence가 아니라
  코드가 확인한 사실(위임·규모·대상 집단)로 한다.

### 6-3. R3 — 사내 규정 영향 분석 (1차)

구성
- `app/policies/corpus/virtual_card_co.json`: **가상** "가상카드(주)" 사내 규정 9종 24개 조. 2026년 개정 이전 기준을 일부러 남긴 조항이 정답이 된다.
- `retriever.py`: 글자 2-gram TF-IDF로 후보 top-5. LLM에 규정집 전체를 넣지 않는다.
- `service.py`: C7 영향 판단 → 코드 검증 → C8 개정 초안 → 코드 검증.
  - 모르는·중복 라벨은 버림. **판단을 빠뜨린 후보는 '관련 없음'이 아니라 NEEDS_REVIEW.**
  - CONFLICT·UPDATE는 법령 원문 **과** 사내 규정 원문 인용이 둘 다 원문에서 확인될 때만 ACTIONABLE. 아니면 NEEDS_REVIEW.
  - 근거 범위 밖 조문번호, 초안의 근거 없는 수치("120일" 안의 "20일"은 근거가 아니다)를 잡는다.
- `workflow.py`: DRAFTED → IN_REVIEW → APPROVED | REJECTED(→ 사람이 고쳐 DRAFTED). 승인·반려는 준법감시인만, **제출자는 자기 초안 승인 불가(4-eyes)**,
  검증 문제가 붙은 초안은 문제를 확인했다고 표시해야 승인. 감사 로그는 추가 전용 해시 체인 — 중간 수정·삭제 시 끊긴 위치를 돌려준다.
- 테스트 16개(LLM 없이), 재생 회귀 테스트 2개.

평가 `policy_impact_v1` (gpt-4o, 라벨은 첫 실행 전 확정, dev 6건·sealed 12건)

| 지표 | dev (2회 실행, 프롬프트 1회 수정) | **sealed (1회 실행, 소진)** |
|---|---|---|
| 검색 재현율 | 66.7% (2/3) | 100% (4/4) |
| 조치 재현율 (양쪽 근거 확인된 ACTIONABLE) | 66.7% | **50%** (2/4) |
| 사람 검토 포함 재현율 (ACTIONABLE + NEEDS_REVIEW) | 66.7% | **100%** (4/4) |
| 조치 정밀도 | 66.7% | **50%** (2/4) |
| 음성 대조군(무관 법령) 오조치 | 0/1 | 0/3 |
| 모델 인용 정확도 | 100% | 79.3% |
| 초안 필수 수정 충족 | 2/2 | 2/2 |
| 비용 | ≈$0.07 + 수정 후 재녹화 | ≈$0.15 |

읽는 법
- **봉인셋에서 고쳐야 할 조항 4개는 전부 사람 눈에 띄었다.** 2개는 근거가 확인된 조치 대상으로, 2개는 인용이 원문과 맞지 않아 NEEDS_REVIEW로.
- 인용 탈락의 원인은 내용이 아니라 **형식**이었다: 프롬프트에 넣은 사내 규정 머리말("채용관리지침 제9조(…) · 소관 인사팀")을 인용에 포함, 조문 제목과 떨어진 항을 이어 붙임.
  검증이 이를 막은 것은 맞는 동작이지만, 정상 근거가 사람 검토로 밀린다. **sealed를 본 뒤의 수정이므로 v2에서 잰다.**
- 오조치 2건(산업안전보건법 제24조 → SH-01 제6조, 정보통신망법 제45조 → IS-01 제8조)은 부합하는 조항에 "보완 권고"를 낸 과잉 판단이다. dev의 같은 유형(D2 → PR-01 제5조)도 프롬프트 수정 후 남았다.
  런타임에서 막을 수 없는 종류(부합을 원문으로 반증할 수 없다)라 평가로만 보인다.
- 검색 실패 1건(채용절차법 제4조의3 → HR-02 제5조): 법은 "용모·키·체중·출신지역·혼인여부", 규정은 "본적·가족관계·신장·체중" — 어휘가 거의 안 겹친다.
  법령명을 질의에 넣어 봐도 안 잡혔다. 조문 단위 임베딩이나 용어 사전이 필요하다.

### 6-4. R3 2차 — v1 봉인셋의 실패를 고치고 새 봉인셋으로 잰다 (policy_impact_v2)

순서: v1 sealed 결과 확인 → **v2 sealed 15건 라벨 확정(모델 실행 전)** → 수정 → v2 dev(= v1 18건 전체)로 확인 → v2 sealed 1회.
사내 규정집 v2 = v1 + 8개 조(연차·육아휴직·성희롱 조치·임금명세·기간제·근로조건 명시·연장근로·퇴직급여). v1 평가는 v1 규정집 그대로 둔다.

수정
1. **인용 구간 분리** (`segment_spans`): 줄바꿈·항 번호(①)·호 번호("1. ") 경계에서 나눠 조각마다 원문 대조. 원문에 없는 조각은 여전히 탈락한다 — 완화가 아니라
   이어 붙여 생긴 '연속된 문장'이라는 거짓 모양만 없앤다. 후보 머리말과 원문을 `원문:`으로 갈라 보여준다.
2. **반론 검토 C7b**: ACTIONABLE마다 "고칠 필요가 없을 가능성"을 먼저 찾는 두 번째 판단. DISPUTE면 버리지 않고 NEEDS_REVIEW.
   CONFIRM이어도 빠진 법 요구를 원문으로 짚지 못하면 NEEDS_REVIEW. 부합을 원문으로 반증할 수 없는 과잉 판단을 거르는 장치.
3. UPDATE_RECOMMENDED 기준: 법이 **명시한** 구체 요구 중 빠진 것을 짚을 수 있을 때만.

| 지표 | v1 sealed (12건) | v2 dev (18건, 2회) | **v2 sealed (15건, 1회, 소진)** |
|---|---|---|---|
| 조치 재현율 (근거 확인된 ACTIONABLE) | 50% | 85.7% (놓친 1건은 검색 실패) | **100%** (6/6) |
| 사람 검토 포함 재현율 | 100% | 85.7% | 100% |
| 조치 정밀도 | 50% | 85.7% (C7b 전 60%) | **75%** (C7b 전 50%) |
| 음성 대조군 오조치 | 0/3 | 0/4 | 0/3 |
| 모델 인용 정확도 | 79.3% | 98.7% | 97.4% |
| 초안 필수 수정 충족 | 2/2 | 6/6 | 6/6 |
| 비용 | ≈$0.15 | — | ≈$0.26 |

- C7b가 v2 sealed에서 과잉 판단 4건을 사람 검토로 돌렸다(정밀도 50 → 75%). 진짜 개정 대상을 반박한 경우는 0건.
- 남은 오조치 2건: 육아휴직 조문 → 기간제 계약기간 조항(검토자도 CONFIRM), 연장근로 조문 → 12시간 한도 조항. **v3에서 잰다.**
- 비용: C7b는 ACTIONABLE마다 호출 1회 추가. v2 sealed에서 전체 비용 ≈$0.26/15조문.

### 6-5. R3 저장·API (구현)

- `migrations/008_policy_workflow.sql`: `org_members`(역할), `policy_drafts`, `policy_draft_comments`, `policy_audit_events`.
  DB가 막는 것: 4-eyes CHECK, 결정 상태엔 결정자 필수, 감사 이벤트 UPDATE·DELETE 트리거 거부, 조직별 (org_id, seq) 기본키.
- `app/policies/postgres.py`: 상태 전이 + 감사 이벤트를 한 트랜잭션에. 전이는 `WHERE state = 읽은 상태`(낙관적 동시성) — 두 준법감시인이 동시에 결정하면 하나만 성공.
  체인 끝을 읽고 쓰는 사이는 조직 단위 advisory lock.
- 같은 계약 테스트를 메모리·Postgres 양쪽에 돌린다(`tests/test_policy_workflow_repo.py`, 로컬 Postgres 17에서 확인).
- API `/api/v1/policy/*` (문서 05 §4-7). 초안 생성 때 서버가 영향 판단을 다시 돌린다 — 클라이언트가 보낸 판단을 믿지 않는다.

### 6-7. R3 3차 — 허용 규정을 '누락'으로 읽는 과잉 판단 (policy_impact_v3)

v2 봉인셋 오조치 2건을 다시 읽었다.
- **T7은 모델의 오류**: 근로기준법 제53조 ④ "고용노동부장관의 인가를 받아 … 연장할 수 있다"(허용)를 규정이 쓰지 않았다고 '보완 권고'. 회사는 허용된 제도를 쓰지 않을 수 있다.
- **T2는 라벨 오류로 판단**: 남녀고용평등법 제19조 ⑤ "기간제근로자의 육아휴직 기간은 기간제법 제4조 사용기간에서 제외한다"가 기간제 계약기간 조항에 직접 해당한다.
  라벨을 정할 때 조문 앞부분만 읽어 ⑤항을 놓쳤다. 규칙대로 v2 라벨은 바꾸지 않고 v3 데이터셋 `adjudication`에 메모만 남겼다. **v3 라벨은 조문 전문을 읽고 정했다.**

수정 (v3 sealed 라벨 확정 뒤)
- C7·C7b 프롬프트: 법이 "~할 수 있다"로 허용만 하는 제도·예외를 두지 않은 것은 누락이 아니다.
- 코드 검사 `is_obligation`: '보완 권고'의 법 근거(그리고 검토자가 짚은 빠진 요구)가 **전부 허용 규정**이면 NEEDS_REVIEW.
  기본은 의무로 보고 "수 있다"이면서 제한 표지가 없을 때만 허용으로 본다 — 한국 법령은 "2년을 초과하지 아니하는 범위 안에서 … 사용할 수 있다",
  "25일을 한도로 한다"처럼 제한을 허용형으로 쓴다(dev에서 처음 판별기가 진짜 충돌 2건을 놓쳐 발견·수정). CONFLICT에는 적용하지 않는다.

| 지표 | v3 dev (= v2 sealed 15건) | **v3 sealed (11건, 1회, 소진)** |
|---|---|---|
| 조치 재현율 | 100% (6/6) | **100%** (4/4) |
| 조치 정밀도 | 75% (재검토 메모 반영 시 87.5%) | **80%** (4/5) |
| 허용 규정 함정 5개 조항 | — | **5/5 조치 대상에서 걸러짐** (코드 2, 반론 검토 3 → 사람 검토) |
| 음성 대조군 오조치 | 0/3 | 0/3 |
| 인용 정확도 | 97.2% | 100% |
| 초안 필수 수정 충족 | 6/6 | 4/4 |
| 비용 | — | ≈$0.18 |

- 남은 오조치 1건: 근로기준법 제74조 ⑦(임신 중 1일 2시간 근로시간 단축 '허용하여야')를 근로시간 조항(HR-01 제10조)에 '보완 권고'. 판단이 갈릴 수 있어 라벨은 두고 메모만 남겼다.
- 봉인셋 추이: v1 재현 50%·정밀 50% → v2 100%·75% → v3 100%·80%. 각 봉인셋은 한 번만 열었고, 수정은 항상 다음 봉인셋 라벨을 확정한 뒤에 했다. 표본이 작다(11~15건).

### 6-6. R4 — 운영 지표 (구현)

"판정 하나에 얼마가 들고 어디서 실패하는가"를 질의로 답한다.

- 단가표를 `app/core/pricing.py` 한 곳으로 모았다. 평가 결과와 운영 trace가 같은 표를 쓴다. 표에 없는 모델은 비용 0이 아니라 NULL(0이면 '공짜'로 읽힌다).
- trace 행마다 `cost_usd`, `prompt_version`(프롬프트 파일 해시 12자리), `attempt`(REJECT 재생성 회차). `migrations/009`.
- **Validator(C6)도 행을 남긴다**: `model='rules'`, `ok`=거부 여부, `error`=거부 사유. LLM 호출 수·실패 수에는 세지 않는다(의미를 섞지 않는다).
  규칙 검증 시간은 LLM 지연 합계에서 뺐다 — 실측 시간이 섞이면 녹화 재생 회귀 기준이 실행마다 흔들린다.
- `scripts/trace_report.py --chains`(체인별 비용) · `--validator`(거부 사유 순위, 첫 시도 거부 → 재생성 통과 비율) · `--versions`(프롬프트 버전별 실패율·비용).
- 요청 단위 지연: 모든 응답에 `Server-Timing: app;dur=…`, 로그 한 줄(라우트 템플릿으로 남겨 ID가 쌓이지 않음), 5초 이상은 WARNING.
- 사내 규정 API(C7·C7b·C8) 호출도 같은 ai_traces에 저장한다(analysis_id 없음, law_id·article_no로 묶임).

### 6-8. 화면 (구현)

- 결과 상세(판정 '해당')에 **사내 규정 영향** 패널: 후보 조항별 개정 대상 / 사람 검토 / 조치 불필요, 법령·규정 원문 인용, 검증 문제, `개정 초안 만들기`.
- `/policy`: 초안 목록(상태·검증 문제 수), 감사 로그와 해시 체인 검증 결과.
- `/policy/[draftId]`: 현행 ↔ 개정안 어절 단위 비교(삭제 빨강·추가 초록), 상태별 버튼(검토 요청 / 승인·반려 / 고치기), 의견, 이 초안의 감사 기록.
  권한은 서버가 판단하고, 막히면 서버 사유를 그대로 보여준다(화면이 권한을 추측하지 않는다).
- 로컬 dev 모드 전용 사용자 전환(설정 화면): 4-eyes 시연에 두 번째 사용자가 필요하다.
- 확인(2026-10-11, 로컬 Postgres + 프로덕션 빌드): 검토 요청 → 현업 계정 승인 시도 "승인·반려는 준법감시인만 할 수 있다" → 준법감시인 전환 → 승인 → 감사 로그 체인 검증 통과 3건.
