프로젝트 기획서와 「02. 사용자 페르소나 & 유스케이스 정의서」를 기준으로, 개발 착수 전에 확정해야 할 기능 요구사항(FR), 비기능 요구사항(NFR), 우선순위, 수용 기준(Acceptance Criteria), 예외·실패 처리 기준을 정의한다.

Document Purpose

## 1. 문서 목적

본 문서는 “무엇을 만들어야 하는가”를 구현 가능한 단위로 확정하고, 설계·개발·테스트의 공통 기준으로 사용한다.

#### 개발 기준

Frontend, FastAPI, LangChain, RAG, DB 개발자가 동일한 기능 범위와 완료 조건을 공유하도록 한다.

#### 테스트 기준

각 요구사항에 Acceptance Criteria를 연결해 기능 완료 여부를 객관적으로 판정할 수 있게 한다.

#### 변경관리 기준

개발 중 기능 추가/삭제가 발생하면 요구사항 ID 단위로 영향 범위와 관련 Use Case를 추적한다.

> **핵심 원칙:** 이번 프로젝트는 AI Core만 검증하는 과제가 아니라, 로그인 → 프로필 → 규제 분석 → AI 판정 → 근거 확인 → 저장/히스토리까지 E2E로 동작하는 Full-stack AI SaaS 완성을 목표로 한다.

Functional Requirements

## 4. 기능 요구사항 (FR)

### 4-1. 인증·사용자 프로필

**FR-001. 사용자 인증MUST** Related UC** UC-01** Layer** Frontend / Auth / Backend** Source** 기획서 · Persona** Priority** Must**

**요구사항:** 사용자는 로그인/로그아웃할 수 있어야 하며 사용자별 데이터가 분리되어야 한다.

#### Acceptance Criteria

- 인증되지 않은 사용자가 보호된 Dashboard/History URL에 접근하면 로그인 흐름으로 이동한다.
- 로그인 성공 후 현재 사용자 식별자가 프로필·분석·저장·피드백 데이터에 연결된다.
- 로그아웃 후 보호 리소스에 접근할 수 없다.

**FR-002. 업무 프로필 생성/조회/수정MUST**

**요구사항:** 사용자는 직무, 업종, 회사 규모, 관심 영역을 입력·조회·수정할 수 있어야 한다.

#### 필수 데이터

- job
- industry
- company_size
- interests

#### Acceptance Criteria

- 최초 로그인 시 프로필이 없으면 Onboarding을 우선 노출한다.
- 필수값 누락 시 저장할 수 없고 오류 필드가 표시된다.
- 프로필 변경 이후 새 분석은 변경된 값을 사용한다.
- 기존 분석 이력은 당시 프로필/분석 결과 기준으로 보존된다.

### 4-2. 규제 분석 실행

**FR-003. 새 규제 분석 실행MUST** Related UC** UC-02** Layer** Frontend / FastAPI / AI** Output** analysis_id** Status** queued/running/completed/failed**

**요구사항:** 사용자는 지정된 분석 기간 또는 최신 기준으로 규제 변화 분석을 실행할 수 있어야 한다.

#### Acceptance Criteria

- 분석 요청 시 고유 analysis_id가 생성된다.
- 분석 상태가 최소 queued/running/completed/failed 중 하나로 관리된다.
- 분석 완료 시 결과가 사용자 계정과 연결되어 저장된다.
- 중복 클릭 등으로 동일 요청이 무제한 중복 실행되지 않도록 UI 또는 API에서 방지한다.

**FR-004. 공식 법령 데이터 수집 및 snapshot 저장MUST**

**요구사항:** 시스템은 분석에 사용한 법령명, 조문번호, 시행일, 원문, 변경 관련 데이터를 공식 법령 데이터 소스에서 확보하고 분석 시점 snapshot을 저장해야 한다.

#### Acceptance Criteria

- 법령 사실 필드는 LLM 출력이 아니라 공식 데이터 계층에서 공급된다.
- 분석 결과가 참조하는 법령 snapshot을 추후 재조회할 수 있다.
- 외부 API 실패 시 임의의 법령 사실값을 생성하지 않는다.

**FR-005. 신구법 변경점 계산MUST**

**요구사항:** 변경 전/후 법령 텍스트의 추가·삭제·수정 차이는 코드 기반 diff로 계산해야 한다.

#### Acceptance Criteria

- LLM이 존재하지 않는 변경점을 만들어서는 안 된다.
- Detail 화면에서 변경 전/후 또는 핵심 diff를 확인할 수 있다.
- AI 실무 영향 설명은 diff 결과를 Context로 받아 생성한다.

### 4-3. AI 관련성 판단

**FR-006. 법령 적용대상 구조화 추출MUST**

**요구사항:** AI는 제공된 조문과 관련 Context에서 적용대상, 조건, 예외, 추가 확인 필요 요소를 Structured Output으로 추출해야 한다.

#### Acceptance Criteria

- 출력은 정의된 Pydantic/JSON Schema를 통과해야 한다.
- 근거가 없는 적용조건은 생성하지 않는다.
- 확정 불가능한 조건은 missing_context 또는 equivalent field로 표현한다.

**FR-007. 사용자 관련성 판정MUST** Related UC** UC-03 / UC-04** Allowed Result** APPLICABLE / HOLD / NOT_APPLICABLE** Input** User + Law Context** Validation** Required**

**요구사항:** 시스템은 사용자 직무·업종·규모와 법령 적용대상을 비교해 해당/보류/무관 중 하나로 판정해야 한다.

#### 판정 규칙

- **해당:** 필수 적용조건과 사용자 정보의 연결이 충분히 확인됨.
- **보류:** 규모/업종/시행령/기타 필수조건 정보 부족으로 확정 불가.
- **무관:** 확인 가능한 조건상 현재 사용자 프로필에 직접 적용되지 않음.

#### Acceptance Criteria

- 판정 결과와 함께 판정 이유 및 참조 근거가 저장된다.
- 불확실한 경우 ‘해당’으로 임의 확정하지 않는다.
- 보류는 추가로 필요한 정보를 명시해야 한다.

**FR-008. 보류 사유 및 재판정MUST**

**요구사항:** 보류 결과는 사용자에게 부족한 정보와 보류 이유를 보여주고, 추가정보 입력 후 재판정할 수 있어야 한다.

#### Acceptance Criteria

- 보류 상세 화면에 missing context가 사용자 이해 가능한 형태로 노출된다.
- 추가정보 입력 후 동일 법령에 대해 새 판정을 실행할 수 있다.
- 기존 판정 결과를 덮어쓰기만 하지 않고 변경 이력을 추적할 수 있다.

### 4-4. 실무 영향·대응안

**FR-009. 직무/업종별 실무 영향 생성MUST**

**요구사항:** AI는 법령 변경 내용과 사용자 Context를 기반으로 영향을 받을 수 있는 업무·프로세스·내부 문서를 설명해야 한다.

#### Acceptance Criteria

- AI 해석과 공식 법령 사실값이 UI와 데이터 모델에서 구분된다.
- 법률 자문이나 확정적 법적 결론으로 표현하지 않는다.
- 근거 Context가 없는 실무 조치를 단정하지 않는다.

**FR-010. 행동 등급 분류MUST**

**요구사항:** 관련 규제는 최소 ACTION / DECISION / AWARENESS 중 하나로 분류되어야 하며 보류 상태는 별도 처리해야 한다.

#### Acceptance Criteria

- Dashboard에서 ACTION과 DECISION이 AWARENESS보다 우선 노출된다.
- 각 결과는 action_grade와 설명을 가진다.
- 보류 결과는 행동 등급 확정보다 보류 사유 해소를 우선한다.

**FR-011. 실행 체크리스트 제공SHOULD**

**요구사항:** ACTION/DECISION 결과는 사용자가 검토할 수 있는 실행 항목 또는 확인 항목을 구조화해 제공해야 한다.

#### Acceptance Criteria

- 체크리스트 항목은 법령 사실값과 별도 필드로 관리된다.
- 체크리스트가 없는 경우 억지로 생성하지 않는다.
- 사용자는 적어도 화면에서 항목을 구분해 확인할 수 있다.

### 4-5. Evidence / RAG

**FR-012. 공식 법적 근거 표시MUST**

**요구사항:** 결과 상세 화면에서 법령명, 조문번호, 시행일, 원문 인용 또는 원문 접근 정보를 확인할 수 있어야 한다.

#### Acceptance Criteria

- 법적 근거는 공식 데이터 소스에서 제공된 값만 사용한다.
- 인용문은 저장된 원문 내부에 실제 존재하는지 Validator로 확인한다.
- 검증 실패한 인용은 성공 결과로 노출하지 않는다.

**FR-013. RAG 참고자료 검색MUST**

**요구사항:** 시스템은 정부 가이드, FAQ, 행정해석, 보도자료 등 검증된 참고자료를 의미검색하고 관련 자료를 반환해야 한다.

#### Acceptance Criteria

- 각 문서는 최소 source, agency, published_at, doc_type, vector_id 또는 equivalent metadata를 가진다.
- 검색은 Top-K 및 가능한 경우 법령명/업종/문서유형 metadata filter를 사용한다.
- 검색 결과가 없으면 “참고자료 없음”으로 처리하며 LLM이 존재하지 않는 출처를 생성하지 않는다.

**FR-014. 법적 근거와 참고자료 분리 표시MUST**

**요구사항:** 공식 법령 원문, RAG 참고자료, AI 해석은 화면에서 서로 다른 섹션으로 표시되어야 한다.

#### Acceptance Criteria

- 사용자가 어떤 정보가 공식 원문이고 어떤 정보가 AI 해석인지 구분 가능하다.
- RAG 문서가 법령 원문과 동일한 법적 권위처럼 표현되지 않는다.

### 4-6. Dashboard / History / Feedback

**FR-015. 규제 DashboardMUST**

**요구사항:** 사용자는 최근 분석 결과를 관련성 및 행동 등급 기준으로 요약·필터링하여 볼 수 있어야 한다.

#### Acceptance Criteria

- ACTION / DECISION / AWARENESS / HOLD 개수를 식별할 수 있다.
- 각 결과 카드에서 법령명, 시행일, 판정, 우선순위를 최소 확인할 수 있다.
- 무관 항목은 기본 우선순위가 낮거나 접힌 상태로 제공된다.

**FR-016. 규제 상세 화면MUST**

**요구사항:** 사용자는 개별 규제에 대해 변경 내용, 관련성 이유, 실무 영향, 행동 등급, Evidence를 한 흐름에서 확인할 수 있어야 한다.

**FR-017. 규제 저장/북마크SHOULD**

사용자는 관심 규제를 저장하고 다시 조회할 수 있어야 하며 필요 시 개인 메모를 저장할 수 있다.

**FR-018. 분석 HistoryMUST**

**요구사항:** 사용자는 이전 분석 목록과 결과를 다시 확인할 수 있어야 한다.

#### Acceptance Criteria

- 분석일, 분석 기간, 상태, 주요 결과 요약을 조회할 수 있다.
- 과거 분석은 당시 snapshot과 결과를 기준으로 재현 가능해야 한다.

**FR-019. 사용자 피드백SHOULD**

사용자는 개별 AI 결과에 대해 유용/부정확 여부, 오류 유형, 선택적 코멘트를 제출할 수 있어야 한다.

### 4-7. Validator / Guardrail

**FR-020. 금지 필드 생성 차단MUST**

**요구사항:** LLM은 법령명, 조문번호, 시행일, 원문, 기관, 공식 URL 등 사실 필드를 새로 생성하지 못하도록 구조적으로 제한한다.

#### Acceptance Criteria

- 사실 필드는 별도 데이터 계층에서 주입한다.
- LLM 응답 schema에 불필요한 공식 사실 필드를 두지 않거나 validator가 원천 데이터와 대조한다.
- 위조/불일치가 발견되면 결과 생성 실패 또는 해당 필드 제거로 처리한다.

**FR-021. 인용 검증MUST**

**요구사항:** AI가 제시한 법령 인용은 공식 snapshot에 실제 존재하는 문자열인지 자동 검증해야 한다.

**FR-022. 검증 실패 결과 차단MUST**

**요구사항:** Structured Output 파싱, 인용 검증, 금지 필드 검증 등 핵심 Validator를 통과하지 못한 결과는 정상 분석 결과로 저장/노출하지 않는다.

Non-Functional Requirements

## 5. 비기능 요구사항 (NFR)

| ID      | 영역           | 요구사항              | 목표/Acceptance Criteria                                                                            | 우선순위   |
|---------|----------------|-----------------------|-----------------------------------------------------------------------------------------------------|------------|
| NFR-001 | **정확성**     | 조문 인용 정확도      | 검증된 평가셋 기준 목표 100%. 인용은 원문 substring 검증.                                           | **MUST**   |
| NFR-002 | **정확성**     | 적용 판정 오탐 관리   | 평가셋 기준 FP ≤ 5% 목표. 실측치는 테스트 보고서에 별도 기록.                                       | **MUST**   |
| NFR-003 | **재현율**     | 관련 법령 누락 최소화 | 평가셋 기준 관련 법령 Recall ≥ 90% 목표.                                                            | **MUST**   |
| NFR-004 | **안전성**     | 금지 필드 유출        | 평가 케이스에서 LLM 생성 공식 사실 필드 0건 목표.                                                   | **MUST**   |
| NFR-005 | **신뢰성**     | 실패 시 fail-safe     | 외부 API/LLM/RAG/Validator 실패를 성공 결과로 위장하지 않음.                                        | **MUST**   |
| NFR-006 | **응답성능**   | 대화형 UI 체감 응답   | 분석은 상태를 표시하고 장시간 무응답 UI를 만들지 않음. 실제 latency는 평가 보고서에서 p50/p95 측정. | **MUST**   |
| NFR-007 | **보안**       | 사용자 데이터 격리    | 인증 사용자별 데이터 접근 제어. 다른 사용자 profile/analysis/history 직접 조회 불가.                | **MUST**   |
| NFR-008 | **보안**       | 비밀정보 관리         | API Key/DB Secret은 소스코드/클라이언트 번들에 하드코딩하지 않음.                                   | **MUST**   |
| NFR-009 | **관측성**     | AI Chain 추적         | 최소 요청 단위 latency, model, token/usage, error, trace 식별 가능.                                 | **MUST**   |
| NFR-010 | **테스트성**   | 자동 테스트           | pytest, Front unit/component, Playwright E2E 중 핵심 흐름 자동화.                                   | **MUST**   |
| NFR-011 | **유지보수성** | 모듈 경계             | 법령 수집, RAG, AI 판단, Validator, API, UI 책임이 분리된 구조.                                     | **MUST**   |
| NFR-012 | **확장성**     | 모델 교체 가능성      | LLM provider/model 교체가 비즈니스 로직 전체 수정으로 이어지지 않도록 추상화.                       | **SHOULD** |
| NFR-013 | **UX**         | 상태 가시성           | loading/empty/error/HOLD/completed 상태가 명확히 구분.                                              | **MUST**   |
| NFR-014 | **접근성**     | 기본 웹 접근성        | 키보드 접근, label, 대비, 의미 있는 상태 텍스트를 기본 준수.                                        | **SHOULD** |
| NFR-015 | **법적 고지**  | 법률 자문 오인 방지   | 서비스가 법률 자문이 아닌 AI 기반 규제 모니터링/업무 참고 도구임을 명시.                            | **MUST**   |

> **주의:** NFR-001~004의 수치는 현재 기획서에 정의된 목표값이며 실제 달성값이 아니다. 구현 후 평가 데이터셋에서 측정한 값은 「테스트·평가 보고서」에 별도로 기록한다.

Data & Business Rules

## 6. 핵심 데이터/비즈니스 규칙

| ID     | 규칙                               | 설명                                                                                           |
|--------|------------------------------------|------------------------------------------------------------------------------------------------|
| BR-001 | **공식 사실값은 공식 데이터 우선** | 법령명/조문/시행일/원문/기관/공식 URL은 LLM이 생성하지 않는다.                                 |
| BR-002 | **diff는 코드 계산**               | 신구법 변경 감지는 deterministic logic이 담당한다.                                             |
| BR-003 | **불확실하면 HOLD**                | 필수 적용 조건이 부족하면 해당으로 확정하지 않는다.                                            |
| BR-004 | **법적 근거와 RAG 참고자료 분리**  | 공식 법령 원문과 실무 참고자료의 권위/성격을 혼합하지 않는다.                                  |
| BR-005 | **RAG 결과 없음은 정상 상태**      | 검색 결과가 없을 수 있으며 LLM이 없는 참고자료를 채우지 않는다.                                |
| BR-006 | **분석 당시 근거 보존**            | 과거 분석은 당시 사용한 법령 snapshot과 결과를 연결해 보존한다.                                |
| BR-007 | **행동 등급과 적용 판정 분리**     | APPLICABLE/HOLD/NOT_APPLICABLE와 ACTION/DECISION/AWARENESS는 서로 다른 필드/개념으로 관리한다. |
| BR-008 | **보류 재판정 이력 보존**          | 추가정보 입력 전후 판정 변화를 추적할 수 있어야 한다.                                          |

## 7. 예외 및 실패 처리 요구사항

| ID     | 상황                        | 시스템 동작                                                              | 사용자 표시                               |

| ER-003 | Structured Output 파싱 실패 | 정상 결과 저장 금지. 필요한 경우 제한된 재호출.                          | 분석 실패 또는 일부 항목 처리 실패.       |
| ER-004 | Validator 실패              | 해당 결과 차단.                                                          | 검증 실패로 결과를 제공할 수 없음을 표시. |
| ER-005 | RAG 결과 0건                | 빈 배열 반환. AI가 참고 출처를 생성하지 않음.                            | “관련 참고자료를 찾지 못했습니다.”        |
| ER-006 | 사용자 프로필 부족          | 관련성 판단에서 HOLD 가능.                                               | 필요한 추가정보를 구체적으로 요청.        |
| ER-007 | 인증 만료                   | 보호 API 접근 거부.                                                      | 재로그인 유도.                            |
| ER-008 | DB 저장 실패                | 성공 응답을 반환하지 않음. trace/error 기록.                             | 저장/분석 완료 실패 안내.                 |

## 9. 요구사항 문서 완료 기준

#### 기능 범위

핵심 User Journey에 필요한 Must 기능이 FR-001~FR-022로 식별되었다.

#### 신뢰성 범위

AI의 역할과 금지사항, Validator, HOLD, Evidence 분리 원칙이 요구사항에 포함되었다.

#### 검증 가능성

주요 요구사항에 Acceptance Criteria와 테스트 방향이 연결되었다.

#### 설계 준비

다음 단계인 시스템 아키텍처, ERD, API, AI/RAG 설계로 내려갈 수 있는 요구사항 기준이 마련되었다.
