Executive Summary

## 1. 고도화된 서비스 정의

“내 일에 영향을 주는 규제 변화만 골라, 왜 중요한지와 지금 무엇을 해야 하는지를 근거와 함께 알려준다.”

#### AI Core

**직무·업종·규모** 와 실제 법령 변화를 컨텍스트로 넣고, LangChain 체인으로 **해당 / 보류 / 무관** 을 판단한다. 근거 인용과 금지 필드는 코드로 검증한다.

#### 최종 구현 제품

로그인한 사용자의 회사·직무 프로필을 기반으로 최신 규제 변화를 자동 분석하고, **ACTION / DECISION / AWARENESS** 우선순위로 대시보드에 제공한다.

#### 제품 차별점

법령 사실값은 법제처 API, 실무 맥락은 RAG, 판단은 LLM, 위험한 확정은 Validator가 통제하는 **Hybrid AI Architecture** 다.

> **핵심 전략:** AI Core·프론트엔드·백엔드·RAG·DB를 하나의 제품 범위로 구현한다. **노트북은 핵심 체인의 검증용 산출물이고, 실제 최종 결과물은 웹에서 E2E로 동작하는 통합 서비스다.**

### 2-2. 왜 LLM이어야 하는가

- 법령명·시행일·조문번호 조회

- 경계 사례에서 근거 기반 판단

Hybrid RAG Strategy

## 7. RAG 고도화 설계

> **원칙:** RAG는 법령 원문을 “대체”하지 않는다. **법적 근거는 법제처 API** , RAG는 법령만으로 부족한 **실무 맥락** 을 보강한다.

### 7-1. RAG 대상 데이터

| 문서 유형                 | RAG 사용     | 용도                            |
|---------------------------|--------------|---------------------------------|
| 법령 원문/조문번호/시행일 | **API 우선** | 정확한 식별·팩트는 직접 조회.   |
| 정부기관 가이드           | **RAG**      | 적용 방식과 업무 프로세스 보완. → 법제처 `admrul`(훈령·예규·고시) |
| FAQ·행정해석              | **RAG**      | 실무 질문과 유사한 사례 검색. → 법제처 `expc`(법령해석례) |
| 정부 보도자료             | **RAG**      | 개정 목적과 시행 배경 설명. → **미구현** (법제처에 해당 target 없음) |
| 검증된 사례/결정례        | **RAG**      | 업종·상황별 적용 사례 보조. → 법제처 `prec`(판례) |

### 7-2. RAG 파이프라인

    Document Loader
        ↓
    Metadata Normalization
    (source / 기관 / 날짜 / 문서유형)
        ↓
    Text Splitter
        ↓
    Embedding
        ↓
    Pinecone  ← MVP에서는 Chroma/FAISS 가능
        ↓
    Retriever (Top-K + metadata filter)
        ↓
    Context Builder
        ├─ [법적 근거] 법제처 API
        └─ [참고 근거] RAG
        ↓
    LangChain Prompt
        ↓
    LLM + Structured Output
        ↓
    Validator
        ↓
    Frontend Evidence UI

### 7-3. RAG 품질 통제

- 기관/출처/발행일 metadata를 반드시 저장한다.
- Top-K 문서를 사용자 업종·법령명·문서유형으로 필터링한다.
- 법제처 원문과 RAG 참고자료를 동일 “근거”로 섞어 표시하지 않는다.
- RAG 검색 결과가 없으면 모델이 빈 맥락을 추론으로 채우지 않게 한다.

### 11-0-1. RAG 켬/끔 비교 (2026-09-21)

같은 15케이스를 참고자료 유무만 바꿔 측정했다.

| | RAG 끔 | RAG 켬 |
|---|---|---|
| 판정 정확도 | 100% | 100% |
| Q2 오탐률 | 0% | 0% |
| Q4 재현율 | 100% | 100% |
| **Q6 금지 필드 유출** | **0건** | **0건** |
| 참고자료가 붙은 케이스 | 0% | 100% (총 73건) |
| latency p50 | 7,295ms | 6,669ms |

**읽는 법이 중요하다.**

- **RAG가 판정 정확도를 바꾸지 않았다.** 당연한 결과다. 적용 여부는 조문 문언과
  규모 계산으로 결정되고, 그 둘은 이미 결정적 계층이 담당한다. RAG의 가치는
  '실무에서 이 조문을 어떻게 적용하는가'라는 **설명의 질**에 있는데, Q1~Q6는
  그것을 측정하지 않는다.
- **의미 있는 결과는 Q6이 0건을 유지했다는 것이다.** 참고자료 73건을 프롬프트에
  추가로 넣었는데도 모델이 없는 출처나 사실을 만들어내지 않았다. 컨텍스트가
  늘어나면 환각도 늘어나는 것이 일반적이므로, Validator와 프롬프트 경계가
  버텼다는 뜻이다.
- **RAG의 효과는 아직 측정되지 않았다.** 이것이 현재 평가 체계의 가장 큰 공백이며,
  참고자료의 유용성을 재는 별도 평가셋이 필요하다 (07 RAG 설계서 §9).

### 11-0-2. 홀드아웃 실측 — 개발셋 100%는 일반화되지 않았다 (2026-09-21)

§11의 실측은 개발셋에서 나온 값이고, C4 프롬프트를 그 셋의 오답을 보고 두 차례 고쳤다.
편향 없이 재기 위해 **프롬프트 수정에 한 번도 쓰지 않은** 16케이스를 만들어 **한 번만**
돌리고 그 수치를 그대로 기록했다. 법령은 개발셋과 겹치지 않고(최저임금법·채용절차법·
근로자퇴직급여 보장법·건설산업기본법·의료법·파견근로자보호법), 프로필 2종(인력공급,
의료)을 새로 넣었다. 라벨은 실행 전에 확정했다.

**판정 정확도 100% → 62.5%.** 일반화 성능은 62.5%로 읽어야 한다.

**오답 6건이 전부 같은 결함이다.** 6건 모두 정답이 무엇이든 HOLD로 갔고, 위임 유무로
정확히 갈린다.

| 조문 특성 | 케이스 | 정확도 |
|---|---|---|
| 위임 문구 **없음** | 6건 | **100%** (6/6) |
| 위임 문구 **있음** | 10건 | **40%** (4/10) |

위임이 있으면서 정답이 APPLICABLE인 5건은 **5건 모두** HOLD였다. 즉 위임 문구가
감지되고 사용자가 대상 집단에 속하면 APPLICABLE이 나오지 않는다. **ADR-011("적용을
가르는 핵심 기준이 위임되면 보류")을 조건부 원칙이 아니라 무조건 규칙으로 적용하고
있다.** 최저임금법 제6조의 위임은 *산입 임금의 범위*에 관한 것이지 최저임금 지급 의무
자체를 좌우하지 않는데도 보류가 나왔다. 사용자에게는 “최저임금을 줘야 하는지 모르겠다”는
답이 되므로 제품으로서 실패다.

개발셋에는 이 패턴(위임 있음 + 정답 APPLICABLE)이 사실상 없었다. 3회차 프롬프트 수정이
개발셋의 반대 방향 오답만 보고 이뤄져 경계가 한쪽으로 치우친 채 100%가 나온 것이다.
**이것이 개발셋만으로 튜닝할 때 생기는 전형적인 실패이며, 홀드아웃 없이는 보이지 않았다.**

**이 결함은 이 데이터셋으로 고치지 않는다.** 고치는 순간 홀드아웃이 아니게 된다.
근본 해법은 로드맵의 **법률↔시행령 페어링**이다 — 위임된 하위법령 조문을 함께 제공하면
“위임됐으니 모른다”가 아니라 실제 기준을 보고 판정할 수 있다. 이 실측이 그 작업의
우선순위를 뒷받침하는 근거다.

**RAG는 이 16건에서 0건 검색됐다.** 버그가 아니라 인덱스 커버리지다. 현재 인덱스에는
개발셋 5개 법령의 해석례·판례만 적재돼 있다. 뒤집어 말하면 §11-0-1의 “RAG 켬” 수치는
그 5개 법령용으로 맞춰 적재한 인덱스 위에서 나온 값이며, 임의의 법령을 조회하는 실사용
상황은 오히려 홀드아웃 쪽에 가깝다. 인덱스를 넓히기 전까지 RAG 기여분을 성능으로
주장하지 않는다.

### 11-0. 구현 중 추가된 지표 — 과도한 보류율

기획서 작성 시점에는 없던 지표다. 첫 실측에서 **15건 중 12건이 보류**로 나와, 오탐은

남용하면 “아무것도 판단해 주지 않는 서비스”가 된다.

| 지표 | 정의 | 초기 | 수정 후 |
|---|---|---|---|
| 과도한 보류율 | 보류가 아니어야 할 건을 보류한 비율 | 70% | **0%** |

### 12-0. 순서 변경 기록 — Frontend와 Supabase를 맞바꿈

**원안:** W3 Supabase → W4 Frontend
**변경:** W3 Frontend → W4 Supabase (2026-09-21, W2 완료 시점에 결정)

W2 종료 시점에 인메모리 저장소만으로 로그인 → 프로필 → 분석 → 결과 → 근거 → 저장
흐름이 API로 완전히 관통했다. 즉 **프론트를 붙이는 데 DB가 필요하지 않다.**

순서를 바꾼 이유는 두 가지다.

1. **화면이 API 계약의 빠진 곳을 알려준다.** 지금 API는 요구사항 문서만 보고
   설계했으므로, 실제 화면을 그려봐야 응답에 무엇이 부족한지 드러난다. DB를
   먼저 만들면 그 변경을 스키마에 **두 번** 반영하게 된다.
2. **Supabase 작업은 저장소 구현 교체다.** `app/repositories/`가 Protocol로
   분리되어 있어 프론트 작업과 독립적이며, 나중에 해도 비용이 같다.

**바꾸지 않은 것:** 두 단계 모두 이번 프로젝트의 필수 범위이며, 어느 것도 “추후”로
미루지 않는다. 최종 산출물이 하나의 통합 서비스라는 원칙도 그대로다.

## 13. 수업 발표에서는 무엇을 보여줄 것인가

발표에서는 LangChain 핵심 체인을 중심으로 설명하되, **실제 완성된 Next.js/FastAPI/RAG/DB 통합 서비스** 를 시연한다. 고도화 아키텍처는 미래 계획이 아니라 현재 구현 결과로 제시한다.

0:00** 문제 · 35초**

“내 일에 걸리는 법이 바뀌었는데 나는 모른다.” + 78% 실측.

0:35** 대표 데모 · 1분 20초**

사용자 입력 → 해당 결과 → 조문 근거.

1:55** 입력 비교 · 45초**

이커머스 / 일반 인사 / 방산 SW로 결과가 해당·무관·보류로 갈리는 장면.

2:40** LangChain 설계 · 1분 25초**

Prompt → Structured Output → Validator. RAG/API 경계를 한 문장으로 설명.

4:05** Eval · 35초**

실측 지표와 실패 케이스.

4:40** 고도화 · 20초**

“LangChain AI Core를 FastAPI로 서비스화하고 Next.js 대시보드·RAG·Supabase까지 통합해 실제 웹 서비스로 완성했습니다.”

### 13-1. 발표용 핵심 문장

**AI 필요성**

“이 문제를 검색이 아니라 일반 법령을 내 업무의 의미로 번역하는 문제로 정의했습니다.”

**신뢰성**

“법령명과 조문번호는 모델이 생성하지 않습니다. 공식 데이터가 공급하고 모델은 의미만 판단합니다.”

**RAG**

“법적 근거는 법제처 API, 실무 맥락은 RAG로 분리해 근거의 성격을 섞지 않았습니다.”

**고도화**

“노트북에서 검증한 체인을 FastAPI로 분리하고 Next.js·RAG·DB와 연결해 하나의 SaaS로 완성합니다.”
