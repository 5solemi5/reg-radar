# 02. 사용자 페르소나 & 유스케이스 정의서

프로젝트 기획서의 타깃 사용자와 서비스 가치에 근거하여, 실제 개발 요구사항·화면·AI 판단·테스트의 기준이 되는 사용자 유형과 핵심 사용 시나리오를 정의한다.

문서 상태: 개발 착수 전 기준안 작성 기준일: 2026-09-21 상위 문서: 01. 프로젝트 기획서

Document Purpose

## 1. 문서 목적과 범위

본 문서는 “누가, 어떤 상황에서, 무엇을 해결하기 위해 이 서비스를 사용하는가”를 개발 가능한 수준으로 구체화한다.

#### 요구사항 기준

다음 문서인 요구사항 정의서의 기능 요구사항(FR)과 비기능 요구사항(NFR)을 도출하는 기준으로 사용한다.

#### 제품/화면 기준

Onboarding, Dashboard, Regulation Detail, Evidence, History, Settings 화면의 정보 구조와 우선순위를 결정한다.

#### AI/테스트 기준

해당/보류/무관 판정, ACTION/DECISION/AWARENESS 분류, 근거 확인, 재판정 흐름을 AI 평가 및 E2E 테스트 시나리오로 사용한다.

> **설계 가정:** 아래 인물의 이름·나이·회사명은 기획서에 직접 명시된 사실이 아니라, 기획서의 사용자군을 실제 서비스 설계에 활용하기 위해 만든 대표 페르소나다. 사용자군의 역할·문제·서비스 가치·핵심 행동은 기획서 정의를 따른다.

### P01. 김민지 — 법무 담당자가 없는 온라인 쇼핑몰 대표

Primary Persona · 소상공인/1인 사업자 계열

업무 환경직원 4명 규모 온라인 생활용품 쇼핑몰. 상품 운영, 마케팅, 고객응대, 개인정보, 직원 관리까지 직접 관여. 규제 이해도낮음. 법령명이나 기사 제목은 볼 수 있지만 실제 적용 여부와 실무 조치를 판단하기 어려움. Pain Point“이 법이 우리 사업에도 적용되나?”, “지금 무엇을 바꿔야 하나?”를 확인하기 위해 여러 정부 사이트와 검색 결과를 오가야 함. Goal내 업종·회사 규모에 실제로 해당하는 변화만 빠르게 보고, 해야 할 일을 체크리스트로 확인. 신뢰 조건법령 원문과 출처가 반드시 보여야 하며, 불확실하면 ‘보류’로 명확히 표시되어야 함. 핵심 기능프로필 기반 필터링, 관련성 판정, ACTION 표시, 근거 원문, 보류 재판정. 👩‍💼

### P02. 박준호 — 중소 IT기업 HR 실무자

Primary Persona · 중소기업 직무 실무자 계열

업무 환경직원 80명 IT기업 HR 담당. 채용, 근태, 급여, 근로계약, 취업규칙 관리. 규제 이해도기본 노동법 지식은 있으나 개정 조문을 실제 회사 프로세스와 연결하는 데 시간이 많이 듦. Pain Point개정 사실을 알아도 어떤 양식·규정·업무 프로세스를 수정해야 하는지 판단하기 어려움. Goal내 직무에 영향을 주는 변화와 변경 전후 차이, 검토해야 할 내부 문서/프로세스를 한 화면에서 확인. 신뢰 조건변경 조문, 시행일, 원문, 참고자료의 출처가 구분되어야 함. 핵심 기능직무 매핑, 신구법 비교, DECISION/ACTION 분류, Evidence, History. 🏭

### P03. 이수현 — 중소 제조기업 운영/경영지원 팀장

Secondary Persona · 대표/운영 담당자 계열

업무 환경직원 150명 제조기업 운영팀장. 회사 공통 정책, 리스크, 각 부서 전달 및 대응 일정 조율. 규제 이해도법령 원문을 모두 읽기보다 회사 전체 관점에서 영향도와 우선순위를 빠르게 판단해야 함. Pain Point많은 규제 변화가 한꺼번에 발생하면 무엇을 먼저 대응할지 판단하기 어려움. GoalACTION/DECISION/AWARENESS 기준으로 우선순위를 정하고 관련 부서와 시행일을 파악. 신뢰 조건왜 높은 우선순위인지 설명 가능해야 하며, 원문 근거와 참고자료가 확인 가능해야 함. 핵심 기능Dashboard 요약, 우선순위 필터, 관련 부서/업무 영향, 저장, History.

Detailed Use Cases

## 6. 상세 Use Case 명세

**UC-01. 회원가입/로그인 및 업무 프로필 설정** Actor** 전체 사용자** Trigger** 첫 서비스 이용 또는 프로필 수정** Precondition** 서비스 접근 가능** Postcondition** 개인화 분석용 프로필 저장**

#### 기본 흐름

1.  사용자가 회원가입 또는 로그인한다.
2.  시스템은 직무, 업종, 회사 규모, 관심 규제 영역 입력을 요청한다.
3.  사용자가 값을 입력한다.
4.  시스템이 입력값을 검증하고 사용자 프로필에 저장한다.
5.  사용자는 Dashboard로 이동한다.

#### 대안/예외

필수 정보가 누락되면 저장하지 않고 누락 항목을 표시한다. 회사 규모와 같이 규제 판정에 영향을 주는 항목은 이후 보류 판정 사유가 될 수 있음을 안내한다.

**UC-02. 최근 규제 변화 분석 실행** Actor** 전체 사용자** Trigger** “최근 규제 분석” 실행** Precondition** 로그인 + 최소 프로필 존재** Postcondition** 분석 단위(analysis)와 결과 저장**

1.  사용자가 Dashboard에서 분석 실행을 선택한다.
2.  시스템이 분석 기간과 사용자 프로필을 확정한다.
3.  법제처 OPEN API 기반으로 분석 후보 법령/조문을 조회한다.
4.  법령 snapshot 및 변경 전후 데이터를 구성한다.
5.  후속 AI 판단 체인에 Context를 전달한다.
6.  분석 진행 상태를 사용자에게 표시한다.
7.  완료되면 분석 결과를 저장하고 Dashboard에 표시한다.

#### 실패 흐름

공식 API, 모델, Validator 중 하나가 실패하면 성공 결과처럼 표시하지 않는다. 분석 실패 상태, 재시도 동작, 사용한 기준일/캐시 여부를 표시한다.

**UC-03. 사용자 관련 규제 자동 판정** Actor** 전체 사용자** Trigger** 분석 후보 법령 생성** Precondition** 법령 Context + 사용자 프로필 확보** Postcondition** 해당/보류/무관 판정 저장**

1.  시스템이 법령의 변경 조문과 적용대상 관련 Context를 구성한다.
2.  LLM이 적용대상의 의미를 구조화하여 추출한다.
3.  규칙 및 LLM 판단을 조합해 사용자 직무·업종·규모와 매핑한다.
4.  조건이 충분하면 **해당** 또는 **무관** 으로 판정한다.
5.  규모·업종·시행령 등 핵심 정보가 부족하면 **보류** 로 판정한다.
6.  Validator가 인용 및 금지 필드 생성을 검증한다.
7.  판정 이유와 근거를 결과에 저장한다.

> **핵심 원칙:** 애매한 사례는 “해당”으로 확정하지 않고 “보류”로 내린다.

**UC-04. 보류 사유 확인 및 추가정보 입력 후 재판정** Actor** 전체 사용자** Trigger** 보류 결과 선택** Precondition** 보류 판정 + missing context 존재** Postcondition** 추가정보 기반 새 판정**

1.  사용자가 보류 항목을 연다.
2.  시스템이 “왜 보류인지”와 “판정에 필요한 추가정보”를 표시한다.
3.  사용자가 회사 규모, 업종 세부정보 등 필요한 값을 입력한다.
4.  시스템이 추가정보를 프로필 또는 해당 분석 Context에 반영한다.
5.  관련성 판단 체인을 다시 실행한다.
6.  새 판정과 근거를 표시하고 이력을 보존한다.

**UC-05. 변경 전/후 법령 비교** Actor** 실무자·운영담당** Trigger** 규제 상세 화면 진입** Precondition** 신구법 snapshot 존재** Postcondition** 변경점 이해**

1.  사용자가 Regulation Detail에서 변경 비교를 선택한다.
2.  시스템이 코드 기반 diff 결과를 표시한다.
3.  추가/삭제/수정 구간을 구분해 보여준다.
4.  AI는 diff 자체를 생성하지 않고, 제공된 변경 내용을 기반으로 실무 함의를 설명한다.

**UC-06. 직무·업종별 실무 영향 확인** Actor** 전체 사용자** Trigger** 관련 규제 상세 조회** Precondition** 해당 또는 보류 판정** Postcondition** 업무 영향과 검토사항 확인**

1.  시스템이 사용자 직무·업종 Context와 변경 조문을 결합한다.
2.  LLM이 영향을 받을 수 있는 업무, 내부 문서, 프로세스를 구조화해 생성한다.
3.  모델 해석임을 표시하고 법적 사실 필드와 분리한다.
4.  사용자는 필요한 검토사항을 확인한다.

**UC-07. ACTION / DECISION / AWARENESS 우선순위 확인** Actor** 전체 사용자** Trigger** 분석 완료** Precondition** 관련성 + 실무 영향 결과 존재** Postcondition** 대응 우선순위 확인**

| 등급          | 의미                                             | 사용자 기대 행동                  |
|---------------|--------------------------------------------------|-----------------------------------|
| **ACTION**    | 시행 전 구체적인 조치가 필요한 변화              | 체크리스트 확인 및 즉시 검토/수정 |
| **DECISION**  | 정책/업무 방침의 판단이 필요한 변화              | 내부 의사결정 또는 담당자 검토    |
| **AWARENESS** | 현재 즉시 조치보다는 인지/모니터링이 필요한 변화 | 내용 확인 및 저장                 |
| **HOLD**      | 정보 부족으로 확정할 수 없는 변화                | 추가정보 입력 후 재판정           |

**UC-08. 법령 원문/조문/시행일 확인**

1.  사용자가 Evidence 영역을 연다.
2.  시스템은 법제처 API에서 확보한 법령명, 조문번호, 시행일, 원문을 표시한다.
3.  법적 사실은 AI 설명과 시각적으로 분리한다.
4.  사용자는 공식 근거를 직접 확인할 수 있다.

> **데이터 원칙:** 법령명·조문번호·시행일·원문은 LLM이 새로 생성하지 않는다.

**UC-09. RAG 참고자료 확인**

1.  사용자가 “참고자료” 영역을 연다.
2.  Retriever가 정부 가이드, FAQ, 행정해석, 보도자료 등에서 Top-K 문서를 반환한다.
3.  각 자료에 기관, 출처, 발행일, 문서유형을 함께 표시한다.
4.  법적 근거와 참고자료를 동일한 의미의 근거로 섞지 않는다.
5.  검색 결과가 없으면 “참고자료 없음”으로 표시하고 모델이 임의로 보충하지 않는다.

**UC-10 ~ UC-13. 저장·이력·피드백·재분석**

| ID    | 기본 흐름                                                                | 완료 상태                                  |
|-------|--------------------------------------------------------------------------|--------------------------------------------|
| UC-10 | 사용자가 규제를 저장 → 시스템이 사용자별 북마크와 메모를 저장.           | 저장 목록에서 다시 조회 가능.              |
| UC-11 | 사용자가 History 진입 → 과거 분석 단위와 결과를 조회 → 현재 결과와 비교. | 분석 기준일과 당시 snapshot 확인 가능.     |
| UC-12 | 사용자가 유용/부정확 피드백 및 오류 유형/코멘트 제출.                    | feedback 데이터가 결과 ID와 연결되어 저장. |
