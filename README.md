# 규제 레이더 (Reg Radar)

> 내 업무에 영향을 주는 규제 변화만 골라, **왜 중요한지**와 **지금 무엇을 해야 하는지**를
> 근거와 함께 알려주는 AI 규제 모니터링 서비스.

법령은 계속 바뀌지만, 대부분의 실무자에게는 "그래서 나한테 해당되나?"가 답하기
어려운 질문이다. 이 서비스는 직무·업종·규모를 기준으로 무관한 변화를 걸러내고,
해당하는 것에 대해 **법제처 원문을 근거로** 실무 영향과 대응 우선순위를 제시한다.

```
┌─ 법제처 OPEN API ──→ 법령 원문 · 신구법 변경 구간   [사실]
├─ 코드 ────────────→ 변경 감지 · 규모 기준 판정      [계산]
├─ RAG ─────────────→ 법령해석례 · 행정규칙 · 판례    [맥락]
└─ LLM ─────────────→ 적용 의미 해석 · 실무 영향      [판단]
                            ↓
                      Validator  ← 인용 검증 · 사실 위조 차단
                            ↓
                   해당 / 보류 / 무관 + 행동 등급
```

## 이 프로젝트가 다르게 한 것

### 1. AI가 법령 사실을 만들 수 없다 — 구조로 막았다

LLM 출력 스키마에 `law_name`, `article_no`, `effective_date` 같은 필드가 **아예
없다.** 담을 자리가 없으면 위조도 불가능하다. 법령명·조문번호·시행일은 법제처
API가 공급하고, LLM은 "이 조문이 이 사람에게 어떤 의미인가"만 판단한다.

모델이 자유 서술에 조문번호를 끼워 넣는 경로도 막는다. Validator가 근거 범위 밖
조문번호·날짜·참고자료 인용을 찾아내면 결과를 통째로 거부한다.

### 2. 인용은 원문 대조로 검증한다

AI가 제시한 조문 인용이 실제 원문에 존재하는 문자열인지 substring으로 확인한다.
확인되지 않은 인용은 제거하고, **검증된 근거가 하나도 남지 않은 "해당" 판정은
거부한다.** 근거 없는 확정이 이 서비스에서 가장 위험한 출력이기 때문이다.

### 3. 불확실하면 보류 — 그리고 무엇이 필요한지 말한다

정보가 부족하면 "해당"으로 확정하지 않는다. 보류 판정은 `missing_context`가
비어 있으면 **스키마 단계에서 거부**되므로, 항상 "이 값을 넣으면 풀립니다"를
함께 제시한다.

### 4. 산술은 LLM에 맡기지 않는다

"상시 10명 이상"과 사용자의 80명을 비교하는 일은 의미 해석이 아니라 계산이다.
초기에 이걸 LLM에 맡겼더니 *"상시 10명 이상의 정의가 필요하다"* 며 판단을
회피해 **15건 중 12건이 보류**로 나왔다. 코드로 계산해 사실로 주입하도록 바꿨다.

### 5. 근거의 성격을 섞지 않는다

법제처 원문(법적 근거) · RAG 참고자료(실무 맥락) · AI 해석을 **별도 타입**으로
유지한다. API 응답에서도 별도 키이고, 화면에서도 배지로 구분한다. 프론트엔드가
실수로 섞으려면 의도적으로 합쳐야 한다.

## 측정

설계 목표(Q1~Q6)를 실제 법령·실제 모델로 측정했다. 15케이스 · gpt-4o 기준.

| 지표 | 목표 | 실측 |
|---|---|---|
| Q1 노출 인용 정확도 | 100% | 100% |
| Q2 적용 판정 오탐률 | ≤ 5% | 0% |
| Q3 행동 전환 비율 | ≥ 60% | 100% |
| Q4 관련 법령 재현율 | ≥ 90% | 100% |
| Q5 시행령 위임 감지 | 100% | 100% |
| Q6 금지 필드 유출 | 0건 | 0건 |

**이 수치를 일반화해서는 안 된다.** 평가에 쓴 데이터셋은 개발셋이며 프롬프트를
이 셋의 오답을 보고 수정했다. 표본도 15건이라 1건이 6.7%p를 움직인다. 프롬프트
수정에 쓰지 않은 홀드아웃 셋 구축이 다음 과제다.

측정 방법과 개선 경과는 [`backend/evaluation/README.md`](backend/evaluation/README.md).

## 기술 구성

| 레이어 | 기술 |
|---|---|
| Frontend | Next.js 16 · React 19 · TypeScript · Tailwind 4 · TanStack Query · Zod |
| Backend | FastAPI · Pydantic · LangChain · asyncpg |
| Data | Supabase (PostgreSQL + Auth) · 법제처 OPEN API |
| AI | OpenAI (gpt-4o) · Chroma (벡터 검색) |
| Test | pytest 460 · Playwright E2E 18 |

기본 모델이 `gpt-4o`인 이유는 측정 결과다. `gpt-4o-mini`는 같은 데이터셋에서
Q4 재현율 60%로 요구사항(≥90%)을 충족하지 못했다.

## 실행

```bash
# 백엔드
cd backend
python3 -m venv .venv && .venv/bin/python -m pip install -e ".[dev]"
cp .env.example .env          # OPENAI_API_KEY, LAW_API_OC 입력
.venv/bin/python -m uvicorn app.main:app --port 8000

# 프론트엔드
cd frontend
pnpm install
cp .env.example .env.local
pnpm dev
```

법제처 OC는 [open.law.go.kr](https://open.law.go.kr) 가입 후 발급받는다.

Postgres·Supabase 연동과 배포는 [`backend/README.md`](backend/README.md)와
[배포 가이드](docs/규제변화_AI도우미_MD_문서/08_배포_운영_가이드.md) 참조.

## 알려진 한계

정직하게 남긴다.

- **평가셋이 작고 개발셋이다.** 15건이며 프롬프트를 이 셋에 맞춰 수정했다.
- **RAG의 효과를 측정하지 못했다.** Q1~Q6는 판정을 재는 지표인데 RAG의 가치는
  설명의 질에 있다. 참고자료 73건을 넣고도 Q6이 0건을 유지한 것은 확인했다.
- **위임 조항이 많은 법에서 보류율이 높다.** 구체 기준이 하위법령에 있으면
  설계상 보류가 맞지만, 사용자에게는 보류가 많아 보인다. 법률↔시행령 페어링이
  이를 푸는 열쇠이나 미구현이다.
- **조문 단독 판단의 한계.** 근로기준법 제76조의2처럼 문언에 규모 조건이 없어도
  시행령이 5인 미만을 제외하는 경우를 조문만으로는 알 수 없다.
